# Deferred observability migration

ClickHouse, Loki, Prometheus, Grafana и OTel Collector сейчас не развёрнуты. Метрики/аналитика находятся в PostgreSQL, BO-представление отдаёт Core, а журналы хранятся только локально в journald. Фактическое состояние и операционный долг — в [BO-инструкции](../business-owner-operations.md#известные-операционные-пробелы).

Этот документ сохраняет технический план возможного перехода. Он не утверждает, что подготовительный export, archive или dual-write уже существуют.

## Когда переход оправдан

| Компонент | Измеримый триггер |
| --- | --- |
| Отдельный metrics backend | Запись/чтение инфраструктурных рядов измеримо мешает основным операциям PostgreSQL/Core |
| ClickHouse | Аналитические запросы или retention не укладываются в доступные ресурсы PostgreSQL |
| Loki | Инциденты регулярно требуют одновременного поиска по журналам нескольких хостов и локальной ротации недостаточно |
| Grafana | Core panel перестаёт покрывать согласованные операторские представления |
| OTel Collector | Число producers/backends требует независимого backpressure и routing |

Появление бюджета без измеримого узкого места не является триггером.

## PostgreSQL → ClickHouse

### Инварианты целевой выгрузки

- аналитические данные не соединяются с account/email tables;
- время — UTC, значения счётчиков неотрицательны;
- низкокардинальные измерения остаются строками;
- один export chunk имеет однозначный период и контрольные суммы;
- повторная загрузка периода идемпотентна;
- до переключения чтения работает dual-write или повторяемый export;
- сверяются число строк, сумма bytes и число уникальных privacy-safe идентификаторов по каждому периоду.

Текущая схема PostgreSQL не считается автоматически совместимой с ClickHouse: перед стадией миграции нужен schema audit и явное mapping. Старое предположение о готовых суточных партициях и отдельной analytics database удалено как не соответствующее реализации.

### Последовательность

1. Зафиксировать schema mapping и retention для обоих backends.
2. Создать ClickHouse без публичного доступа.
3. Включить dual-write либо повторяемый export, не отключая PostgreSQL read path.
4. Перенести историю по ограниченным временным chunk.
5. Сверить каждый chunk по согласованным агрегатам.
6. Не менее семи суток сравнивать результаты чтения.
7. Переключить read path с возможностью отката.
8. Удалять старый источник только отдельным решением после срока отката.

Расхождение хотя бы одного периода блокирует переключение; его нельзя «исправить» округлением.

## journald → внешний архив → Loki

### Текущее ограничение

Upload job в Spaces отсутствует. Поэтому первым шагом является не Loki, а privacy-safe внешний архив и проверка, что его можно прочитать. Prefix logs/ сам по себе ничего не сохраняет.

### Контракт будущего архива

- формат JSON Lines, а не бинарный journal;
- разрешённые low-cardinality labels: role, node alias, unit, level;
- запрещены destination, SNI, DNS names, email, IP пользователя, session/analytics ID и полные tokens;
- object key кодирует host role, node alias, UTC date/hour и unit;
- upload повторяем для одного часа без дублирования;
- конечный retention выполняется job или bucket policy и проверяется тестом;
- архив шифруется и остаётся приватным.

Пример структуры:

    logs/<host_role>/<node_alias>/<YYYY>/<MM>/<DD>/<unit>-<HH>.json.gz

### Последовательность Loki

1. Реализовать и принять архив, включая privacy и restore/read test.
2. Поднять Loki без публичного доступа и установить допустимый возраст ingest не меньше возраста переносимого архива.
3. Импортировать ограниченный период с labels, восстановленными из object key.
4. Сверить число строк по unit/hour.
5. Включить dual shipping новых записей.
6. Переключить поиск только после окна сравнения.
7. Сохранить архив как независимый recovery path до отдельного решения.

## Автоматические проверки, которые нужны до миграции

- schema/privacy test запрещает account/email/destination fields;
- export test доказывает повторяемость и контрольные суммы;
- archive test проверяет JSONL, allowlist labels и отсутствие запрещённых данных;
- retention test реально удаляет истёкшие objects;
- restore/import test сравнивает исходный и целевой период.

Пока этих jobs/tests нет, документация должна говорить «проект миграции», а не «готовый архив» или «механическая смена строки подключения».
