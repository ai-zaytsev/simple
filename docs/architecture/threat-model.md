# Threat Model

Модель нарушителя для MVP. Исходит из принципа `assume compromise from day one`: система проектируется так, как будто противник уже внутри клиентской части и уже имеет аккаунт.

## Что Считается Данностью, А Не Риском

Следующее не является гипотезой и не требует доказательства. Это стартовые условия:

- APK скачан, распакован и декомпилирован
- публичные API изучены, включая недокументированные поля
- у противника есть обычный рабочий аккаунт FREE
- IP-адреса нод, выданных этому аккаунту, известны противнику
- известные VPN-адреса сканируются и проверяются активным пробингом
- противник может регистрировать множество аккаунтов
- противник целенаправленно пытается перечислить инфраструктуру
- известные endpoint и домены могут быть заблокированы в любой момент

## Что Прямо Не Является Security Boundary

Архитектура не имеет права опираться на эти свойства как на защиту:

| Не защита | Почему |
| --- | --- |
| Обфускация APK | Замедляет анализ на часы, не меняет исход |
| Неизвестность IP ноды | Раскрывается первым же аккаунтом противника |
| Неизвестность домена | Раскрывается из APK и из трафика |
| Неизвестность REALITY profile | Клиент обязан его знать, значит знает и противник |
| Секретность клиентского протокола | Протокол воспроизводим по клиенту |

Любое проектное решение, единственным обоснованием которого является «противник не догадается», считается дефектом и подлежит замене.

## Цель Защиты

Не «спрятать инфраструктуру навсегда». Цель формулируется через четыре измеримых свойства:

1. **Ограниченный blast radius** — компрометация или блокировка известной части не выводит из строя остальное.
2. **Отсутствие полного раскрытия fleet** — не существует пути получить весь список нод, ни через API, ни через перебор аккаунтов за разумную цену.
3. **Быстрая замена IP и нод** — замена измеряется минутами и является штатной операцией.
4. **Восстановление без выпуска нового APK** — смена конфигурации, точек входа и нод происходит удалённо.

## Защищаемые Активы

| Актив | Где живёт | Последствие компрометации |
| --- | --- | --- |
| Связь email ↔ account | PostgreSQL | Деанонимизация пользователей. Наивысший приоритет |
| Browsing history | Нигде не хранится по построению | Отсутствует как актив, см. [privacy-model.md](privacy-model.md) |
| Список fleet | PostgreSQL, Fleet manager | Массовая блокировка сервиса |
| Ключ подписи планов | Control Plane, HSM-подобное хранение | Подмена конфигурации у всех клиентов |
| APK signing key | Вне CI, у Business Owner | Подмена приложения |
| VPN credentials | PostgreSQL + конфиг ноды | Бесплатное использование, привязка сессий |
| WireGuard mgmt keys | Control Plane и ноды | Доступ к управляющей сети |
| Provider API tokens | Secrets store CI | Удаление или создание инфраструктуры |

## Поверхность Атаки И Контроли

### 1. Публичный API Control Plane

Угрозы: перечисление fleet, brute force логина, спам magic links, разведка через массовые аккаунты, DoS.

Контроли:

- ни один endpoint не возвращает fleet, его размер, соседние ноды или node id в глобальной нумерации. Клиент видит `primary` и два reserve, и ничего больше
- идентификаторы нод в плане — непрозрачные алиасы, не раскрывающие порядковый номер и не позволяющие судить о размере флота
- rate limit на `/auth/request`: по email, по IP, по подсети, по домену почты
- блок-лист одноразовых почтовых доменов
- magic link одноразовый, TTL 15 минут, привязан к device fingerprint запроса
- план выдаётся не чаще, чем задано policy; повторный запрос возвращает тот же план, а не новую тройку нод

### 2. Перечисление fleet через множество аккаунтов

Главная угроза, потому что она разрешена условиями задачи: противник может создавать аккаунты и легально получать по три ноды.

Контроли:

- **Sticky assignment.** Аккаунт закреплён за ячейкой нод детерминированно. Повторные запросы плана не дают новых нод. Единственный способ увидеть новую тройку — новый аккаунт.
- **Exposure budget.** Каждая нода имеет предел числа различных аккаунтов, которым она когда-либо выдавалась. По достижении предела нода перестаёт назначаться новым аккаунтам, продолжая обслуживать существующие. Это превращает перечисление флота из задачи «создать N/3 аккаунтов» в задачу «успеть попасть в первые K аккаунтов каждой ноды».
- **Pool isolation FREE / VIP.** VIP-мощности никогда не выдаются FREE-аккаунтам. Разведка через бесплатные аккаунты не раскрывает платный пул. Чтобы увидеть VIP-ноды, противник обязан платить, и каждая оплата — стоимость и след.
- **Reconnaissance signal.** Аккаунт, получающий план и не создающий трафика, помечается как разведывательный. Признак вычисляется из агрегатов и не требует данных о содержимом трафика. Такие аккаунты переводятся в отдельный пул.
- **Cooldown.** Между верификацией email и первой выдачей плана существует задержка, заданная remote config. Она дешёвая для человека и дорогая для автоматического перебора.

Остаточный риск: противник с большим бюджетом и терпением всё равно узнает существенную часть FREE-пула. Именно поэтому FREE-ноды проектируются как расходуемые, а не как защищаемые, см. [node-lifecycle.md](node-lifecycle.md).

### 3. Активный пробинг ноды

Угроза: сканер проверяет `:443` и пытается отличить VPN от обычного сайта.

Контроли:

- VLESS + REALITY: при неуспешной аутентификации нода ведёт себя как TLS-прокси к реальному внешнему сайту `dest`. Это штатный механизм REALITY, а не самодельная маскировка
- `dest` выбирается как реальный, доступный, правдоподобный для датацентра ресурс; профиль различается между нодами, чтобы одинаковый ответ не стал сигнатурой флота
- `short_id` уникален на ноду
- клиент использует uTLS-отпечаток популярного браузера
- на ноде нет других публичных портов: SSH и управление доступны только через WireGuard

Остаточный риск: корреляционный анализ по длительности и объёму сессий отличает «сайт» от «туннеля». REALITY не решает эту задачу и не заявляет обратного. Ответ архитектуры — не невидимость, а дешёвая замена: см. `disposable nodes`.

### 4. Компрометация или изъятие ноды

Угроза: провайдер выдаёт доступ к VPS, диск изымается, root получен.

Что противник получает: активные `vpn_credential_id` на этой ноде, её WireGuard-ключ, её REALITY private key, транзитный трафик в момент захвата.

Чего противник не получает: email, `account_id`, `analytics_id`, список других нод, историю активности пользователей.

Контроли:

- нода не хранит durable-секретов сверх собственного WG-ключа и node token; конфигурация Xray регенерируется из Control Plane при каждом старте
- нода не знает о других нодах: у неё нет ни реестра, ни маршрутов к соседям
- WG-ключ ноды скоупится только на канал с Control Plane
- при подозрении нода помечается `BLOCKED`, её credentials отзываются, ключ удаляется, клиенты уезжают на reserve
- на ноде нет access log, DNS log и SNI log — изъятие диска не даёт истории

### 5. Компрометация Control Plane

Наихудший сценарий: доступ к PostgreSQL раскрывает связь email ↔ account и весь fleet.

Контроли:

- Control Plane не имеет публично доступных портов, кроме API; управление — только через WireGuard
- шифрование БД at rest, отдельные учётные записи БД на модуль, отсутствие доступа аналитики к таблицам аккаунтов
- ключ подписи планов хранится отдельно от БД и не извлекается процессом приложения в открытом виде дольше, чем нужно для подписи
- аналитическое хранилище физически отдельно и не содержит ключей связи с аккаунтами, см. [identity-model.md](identity-model.md)
- регулярные бэкапы с шифрованием и проверкой восстановления

### 6. Массовая блокировка точек входа

Угроза: блокируются домены Control Plane, диапазоны IP нод или сам протокол.

Контроли: описаны отдельно в [bootstrap-recovery.md](bootstrap-recovery.md). Кратко — несколько независимых точек входа, подписанный bootstrap-дескриптор с anti-rollback и возможность получить конфигурацию через уже работающую ноду.

### 7. Подмена конфигурации у клиента

Угроза: MITM или подставной сервер выдаёт клиенту план, ведущий на ноду противника.

Контроли:

- connection plan подписан Ed25519; публичный ключ вшит в APK
- клиент отклоняет план без валидной подписи независимо от того, по какому каналу он получен
- anti-rollback: план с `seq` меньше сохранённого отбрасывается
- TLS-пиннинг на API Control Plane как второй рубеж, но не как единственный: подпись остаётся действительной и при недоверенном транспорте

Именно подпись, а не транспорт, позволяет безопасно принимать конфигурацию через недоверенные каналы восстановления.

### 8. Злоупотребление сервисом

Угроза: один аккаунт на много устройств, перепродажа, P2P-нагрузка, выжигание канала одним пользователем.

Контроли: лимит одновременных устройств на аккаунт, квоты FREE, классификация нагрузки, приоритет и отдельный пул для тяжёлых пользователей. Детали в [entitlement-model.md](entitlement-model.md) и [observability.md](observability.md).

## Явно Принятые Остаточные Риски

| Риск | Почему принимается |
| --- | --- |
| Перечисление части FREE-пула упорным противником | Стоимость полной защиты выше стоимости замены нод |
| Корреляционный traffic analysis на уровне провайдера | Не решается на уровне MVP; ответ — быстрая ротация |
| Изъятие ноды раскрывает её активные credentials | Ограничено по объёму и лечится ротацией |
| Sideload APK не даёт гарантий целостности среды | Клиент не является security boundary по построению |
| Полная блокировка всех точек входа одновременно | Обрабатывается как инцидент, см. [failure-scenarios.md](failure-scenarios.md) |

Каждый принятый риск имеет владельца и путь пересмотра: любой из них может быть переоткрыт отдельным ADR, если изменится наблюдаемая обстановка.
