# Failure Scenarios

Документ фиксирует, как система ведёт себя, когда что-то сломано. Для каждого сценария определены детект, поведение клиента, реакция системы и путь восстановления.

## Принципы Деградации

1. **Не имитировать успех.** Если туннеля нет, приложение показывает, что его нет. Индикатор `ON` при отсутствии туннеля — дефект.
2. **Не выпускать трафик мимо туннеля.** При обрыве соединение блокируется, а не переключается на прямой канал. Пользователь, считающий себя защищённым, не должен оказаться незащищённым молча.
3. **Недоступность Control Plane не отключает существующих пользователей.** Действует grace-период на последнем валидном плане.
4. **Решения о состоянии инфраструктуры принимаются на агрегате.** Один клиент не выводит ноду из эксплуатации.
5. **Восстановление предпочитает автоматический путь.** Ручное вмешательство — признак недостающей автоматизации, а не нормальный режим.

## Сценарии

### Control Plane временно недоступен

| | |
| --- | --- |
| Детект | Ошибки API у клиентов, падение `connect_attempts` с `entry_kind=https-direct`, алерт по health |
| Клиент | Продолжает работу на текущем плане, переходит в `GRACE`, повторяет попытки с backoff |
| Система | Алерт эксплуатации; новые регистрации и выдача планов недоступны |
| Восстановление | Перезапуск или починка Core; клиенты синхронизируются сами |
| Остаточный эффект | Онбординг новых пользователей приостановлен |

### Домен Control Plane заблокирован

| | |
| --- | --- |
| Детект | Резкое падение успеха `https-direct` в конкретных сегментах при живом сервисе |
| Клиент | Автоматически переходит на `reality-edge`, затем на `tunnel` |
| Система | Ротация домена, выпуск нового bootstrap descriptor с `seq+1` |
| Восстановление | Без новой сборки, см. [bootstrap-recovery.md](bootstrap-recovery.md) |

### Все публичные точки входа заблокированы

| | |
| --- | --- |
| Детект | Провал всех `entry_kind`, кроме `tunnel` |
| Клиент | Поднимает туннель по последнему плану и обращается к Control Plane изнутри |
| Система | Массовый ввод новых edge-нод в других подсетях и у других провайдеров |
| Восстановление | Через канал `tunnel`; для новых установок — канал `rescue` |
| Остаточный риск | Новые установки без плана зависят от `rescue`; пока он не выбран, это известный пробел |

### Одна нода заблокирована

| | |
| --- | --- |
| Детект | Падение `connect_success` по ноде в нескольких сегментах, подтверждение внешней пробой |
| Клиент | Failover на reserve по policy из плана |
| Система | `DEGRADED` → `BLOCKED`, запуск замены, отзыв credentials |
| Восстановление | Новая нода в пул, план обновляется при refresh |

### Все три ноды плана недоступны

| | |
| --- | --- |
| Детект | Клиент исчерпал `primary` и оба reserve |
| Клиент | Запрашивает новый план у Control Plane; при недоступности — обход точек входа |
| Система | Если таких клиентов много, это сигнал массовой блокировки, а не отказа нод |
| Восстановление | Выдача нового плана из здоровых нод; при массовом событии — ввод новых нод |

### PostgreSQL недоступен

| | |
| --- | --- |
| Детект | Ошибки Control Plane, алерт по БД |
| Клиент | Как при недоступности Control Plane, `GRACE` |
| Система | Аутентификация, выдача планов и биллинг остановлены; ноды продолжают обслуживать текущие сессии |
| Восстановление | Починка или восстановление из бэкапа; приоритет выше всех остальных компонентов |

### Email-провайдер недоступен или письма не доходят

| | |
| --- | --- |
| Детект | Падение доли успешных верификаций, ошибки API провайдера |
| Клиент | Показывает честное состояние и предлагает повтор без потери введённого email |
| Система | Алерт; при затяжном отказе — переключение на резервного провайдера |
| Восстановление | Резервный провайдер настраивается заранее как конфигурация, а не в момент инцидента |
| Замечание | Это единственная точка, блокирующая вход новых пользователей полностью, поэтому наличие второго провайдера — не роскошь |

### Нода из экспортированной конфигурации заменена

| | |
| --- | --- |
| Детект | Сторонний клиент пользователя перестал подключаться; в телеметрии — падение обращений по его токену |
| Клиент | Приложение не затронуто: у него свой credential и свой план |
| Система | Subscription-ссылка при следующем обращении отдаёт актуальный набор нод |
| Восстановление | Автоматическое для клиентов с поддержкой подписок; снимки `vless://` и JSON требуют повторной выдачи |
| Замечание | Именно поэтому основным форматом экспорта выбрана subscription-ссылка, а не снимок, см. `ADR-017` |

### Subscription-ссылка опубликована в открытом доступе

| | |
| --- | --- |
| Детект | Резкий рост числа различных источников по одному токену, упор в предел одновременных подключений |
| Клиент | Владелец токена видит, что доступ ограничен, и получает предложение перевыпустить |
| Система | Токен переводится в состояние подозрения; при подтверждении — отзыв; ноды `export`-пула считаются раскрытыми и планируются к замене |
| Восстановление | Перевыпуск токена владельцем, ротация нод `export`-пула |
| Замечание | Ожидаемое событие, а не инцидент: `export`-пул спроектирован как выгорающий быстрее остальных |

### Компрометация ключа подписи планов

| | |
| --- | --- |
| Детект | Инцидент безопасности, аномальные планы, аудит доступа |
| Клиент | Продолжает принимать документы только с известными `key_id` |
| Система | Выпуск нового `key_id`, отзыв старого через remote config, ускоренный refresh |
| Восстановление | Без новой сборки, если второй вшитый ключ валиден; иначе новая сборка |

### Провайдер удалил VPS за abuse

| | |
| --- | --- |
| Детект | Нода исчезла из провайдера, health не приходит |
| Клиент | Failover на reserve |
| Система | `BLOCKED`, замена, при повторении — пересмотр провайдера |
| Восстановление | Штатная замена ноды |

### node-agent жив, Xray упал

| | |
| --- | --- |
| Детект | Самодиагностика node-agent, отсутствие успешных подключений при живом агенте |
| Клиент | Failover на reserve |
| Система | node-agent перезапускает Xray; при повторе — `DEGRADED` |
| Восстановление | Автоматическое; при неуспехе — замена ноды |

### Xray жив, node-agent упал

| | |
| --- | --- |
| Детект | Пропали health-репорты и телеметрия при живом трафике |
| Клиент | Не замечает: туннель работает |
| Система | Нода не получает обновлений конфигурации и не отдаёт метрики, поэтому переводится в `DEGRADED` до восстановления связи |
| Восстановление | Перезапуск агента, при неуспехе — замена ноды |
| Замечание | Учёт трафика за период простоя агента теряется; квоты в этот период считаются неполно |

### Ложное срабатывание деградации

| | |
| --- | --- |
| Детект | Нода помечена `DEGRADED`, но внешняя проба и самодиагностика в норме |
| Клиент | Уже мигрировал на reserve |
| Система | Гистерезис: возврат в `HEALTHY` только после устойчивого окна успеха |
| Восстановление | Пересмотр порогов; массовые ложные срабатывания — повод менять правила, а не отключать детект |

### Наблюдаемость недоступна

| | |
| --- | --- |
| Детект | Нет данных в Grafana, ошибки OTel Collector |
| Клиент | Не затронут |
| Система | Сервис продолжает работать; теряется способность видеть проблемы |
| Восстановление | Починка; буферизация телеметрии на клиенте и ноде в пределах лимита, затем отбрасывание |
| Замечание | Телеметрия никогда не блокирует основной путь: неудача отправки не влияет на туннель |

### Часы устройства сильно расходятся

| | |
| --- | --- |
| Детект | Клиент видит `expires_at` в прошлом при живом сервисе |
| Клиент | Применяет допуск, пытается синхронизироваться с Control Plane, не отключает пользователя молча |
| Система | Отвечает актуальным временем при успешном обращении |
| Восстановление | Автоматическое после первого успешного обращения |

### Версия приложения ниже минимальной

| | |
| --- | --- |
| Детект | `min_supported_app_version` в remote config |
| Клиент | Показывает требование обновиться, не имитирует работу |
| Система | Не выдаёт планы устаревшим сборкам |
| Восстановление | Обновление приложения пользователем |

### Потеря сети на устройстве, смена Wi-Fi на мобильную

| | |
| --- | --- |
| Детект | Клиентские события `reconnect` |
| Клиент | Переустанавливает туннель, не выпуская трафик мимо него |
| Система | Учитывает в `reconnect rate`; всплеск по сегменту — сигнал о проблеме сети, а не ноды |
| Восстановление | Автоматическое |

### Аналитическое хранилище переполнено или недоступно

| | |
| --- | --- |
| Детект | Ошибки записи, рост очереди в OTel Collector |
| Клиент | Не затронут |
| Система | Аналитика деградирует, основной путь не затронут; применяется retention |
| Восстановление | Расширение хранилища или ужесточение retention |

## Сводка По Влиянию

| Компонент | Влияет на существующие туннели | Влияет на новые подключения | Влияет на онбординг |
| --- | --- | --- | --- |
| Control Plane | Нет, до конца `GRACE` | Да | Да |
| PostgreSQL | Нет, до конца `GRACE` | Да | Да |
| Email-провайдер | Нет | Нет | Да |
| Одна VPN-нода | Частично, до failover | Нет | Нет |
| Нода `export`-пула | Только сторонние клиенты | Нет | Нет |
| Все точки входа | Нет, до конца `GRACE` | Частично | Да |
| Observability | Нет | Нет | Нет |

Таблица показывает, что архитектура умышленно смещает риск в сторону онбординга: сломать существующую связность заметно труднее, чем регистрацию нового пользователя.
