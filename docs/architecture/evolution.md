# Evolution Constraints

Business Owner принял два ограничения MVP как временные: один Core-хост и один VPN-транспорт. Условие принятия — архитектура не должна мешать последующему резервированию Core и добавлению альтернативного транспорта.

Документ переводит это условие в конкретные инварианты. Их нарушение не сломает MVP сегодня, но сделает переход дорогим завтра, поэтому они обязательны с первой строки кода.

## Как Читать Этот Документ

| Раздел | Смысл |
| --- | --- |
| Инвариант | Соблюдается **сейчас**, в MVP, при одном Core и одном транспорте |
| Отложено | Не делается в MVP |
| Триггер | Наблюдаемое условие, при котором отложенное перестаёт быть отложенным |

Инвариант — это не «сделать потом». Это то, что стоит дёшево сегодня и дорого послезавтра.

---

## Часть 1. Путь К Резервированию Core

Целевое состояние: несколько равноправных экземпляров Control Plane за общим набором точек входа, работающих с одной базой. Клиент не должен знать, с каким экземпляром он говорит.

### Инварианты, обязательные в MVP

**И-1. Control Plane не хранит состояния в памяти процесса.**
Всё, что переживает запрос, живёт в PostgreSQL. Ни сессий, ни кэша распределения, ни счётчиков, ни очередей в памяти. Допустим только кэш, полная потеря которого не меняет поведения.

**И-2. `seq` генерируется базой, а не процессом.**
Монотонность `seq` для connection plan и remote config обеспечивается транзакцией в PostgreSQL. Счётчик в памяти процесса — прямой путь к тому, что два экземпляра выпустят документы с одинаковым или убывающим `seq` и клиенты начнут отбрасывать валидную конфигурацию как rollback. Это самый дешёвый сегодня и самый болезненный завтра инвариант.

**И-3. Сессии проверяются без привязки к экземпляру.**
Проверка session token не опирается на состояние конкретного процесса: либо подписанный токен, проверяемый локально, либо запись в базе. In-memory session store запрещён.

**И-4. Фоновые циклы защищены блокировкой в базе.**
Оценка здоровья нод, переходы состояний, обработка батчей телеметрии, ротация ключа эпохи — каждый цикл выполняется под advisory lock PostgreSQL. При одном экземпляре это ничего не меняет, при нескольких — предотвращает дублирование и гонки.

**И-5. Никакого состояния на диске Core-хоста.**
Bootstrap descriptor, remote config, реестр нод хранятся в базе, а не в локальных файлах. Локально живут только секреты и конфигурация самого процесса.

**И-6. Rate limit и cooldown считаются в базе.**
Счётчики в памяти при N экземплярах превращают лимит `3 в час` в `3N в час`, то есть тихо отключают защиту от перебора ровно в тот момент, когда система становится популярной.

**И-7. Подпись изолирована за интерфейсом.**
Подписание планов и конфигураций выполняется через один внутренний интерфейс, а не разбросано по коду. Это позволяет позже сделать выделенный подписывающий экземпляр или внешний сервис, не переписывая вызовы.

**И-8. Точки входа — множество с самого начала.**
Bootstrap descriptor уже содержит список `entries`. Несколько Core-серверов выражаются в нём без изменения схемы: это либо несколько `https-direct`, либо балансировщик. Клиент обязан относиться к любым двум точкам входа как к эквивалентным и не иметь привязки к конкретной.

**И-9. Миграции идемпотентны и совместимы с работающей старой версией.**
Схема меняется так, чтобы предыдущая версия приложения Control Plane продолжала работать во время выкладки. Это требование появляется ровно в момент, когда экземпляров становится больше одного, и его нельзя ввести задним числом.

### Отложено

- второй Core-хост и балансировка
- реплика PostgreSQL и автоматический failover базы
- разделение Control Plane на отдельные сервисы

### Триггеры

| Триггер | Что включаем |
| --- | --- |
| Стоимость простоя онбординга превышает стоимость второго хоста | Второй Core + балансировка |
| Время восстановления базы из бэкапа перестаёт быть приемлемым | Реплика PostgreSQL |
| Один компонент Control Plane масштабируется принципиально иначе, чем остальные | Пересмотр `ADR-010` |

Проверка инвариантов И-1 – И-9 обязательна в code review Control Plane. Она дешёвая: каждый пункт проверяется чтением, а не измерением.

## Часть 2. Путь К Альтернативному Транспорту

Целевое состояние: несколько транспортов сосуществуют, сервер выбирает транспорт для конкретного клиента и ноды, а блокировка одного транспорта не выводит сервис из строя.

### Инварианты, обязательные в MVP

**И-10. Транспорт в плане — конверт, а не набор полей верхнего уровня.**

```json
"primary": {
  "alias": "n-7f3a",
  "host": "203.0.113.10",
  "port": 443,
  "transport": {
    "kind": "vless-reality",
    "params": { "credential_uuid": "...", "flow": "...", "server_name": "...",
                "public_key": "...", "short_id": "...", "fingerprint": "chrome" }
  }
}
```

Поля, специфичные для VLESS и REALITY, живут внутри `params` и нигде больше. Схема плана не знает о REALITY ничего, кроме строки `kind`.

**И-11. Клиент объявляет свои возможности.**
Запрос плана содержит `supported_transports`. Сервер выдаёт только то, что клиент умеет. Без этого выкатывание второго транспорта потребует одновременного обновления всех установок, а оно недостижимо.

**И-12. Неизвестный `kind` игнорируется, а не ломает клиента.**
Если в плане пришёл транспорт, которого приложение не знает, эта запись пропускается, а не приводит к отказу всего плана. Это позволяет выдавать смешанные планы во время миграции: `primary` на старом транспорте, reserve на новом.

**И-13. Нода объявляет поддерживаемые транспорты.**
В реестре нода имеет набор `transports`. Fleet manager при выдаче плана пересекает возможности клиента и возможности ноды. При одном транспорте пересечение тривиально, но точка расширения уже существует.

**И-14. Транспорт в клиенте изолирован адаптером.**
Всё, что знает про Xray, libXray, VLESS и REALITY, находится за одним интерфейсом уровня «подними туннель по этому описанию и сообщи о состоянии». Session controller, UI, телеметрия и обработка плана не содержат ни одного упоминания конкретного транспорта.

**И-15. Телеметрия измеряет транспорт отдельно.**
`connect_attempts` содержит `transport_kind`. Без этого поля невозможно ответить на вопрос «падает конкретная нода или падает сам транспорт», а именно этот вопрос определяет момент, когда нужен второй транспорт.

**И-16. Конфигурация ноды хранится по типу транспорта.**
Параметры REALITY хранятся как атрибуты транспорта ноды, а не как отдельные колонки таблицы нод. Добавление транспорта не должно означать миграцию схемы с новыми колонками под каждый протокол.

### Отложено

- реализация второго транспорта
- автоматический выбор транспорта по сетевому сегменту
- одновременное поддержание нескольких транспортов на одной ноде

### Триггеры

| Триггер | Что включаем |
| --- | --- |
| Устойчивое падение connect success по нескольким провайдерам и сегментам, не объясняемое блокировкой конкретных IP | Второй транспорт |
| Разница в connect success между сегментами устойчиво выше порога | Выбор транспорта по сегменту |
| Замена нод перестаёт восстанавливать доступность | Экстренный ввод второго транспорта |

Именно И-15 делает эти триггеры измеримыми. Без него решение о втором транспорте принималось бы по ощущениям.

## Сводка Стоимости

| Инвариант | Стоимость сегодня | Стоимость введения задним числом |
| --- | --- | --- |
| И-2 `seq` в базе | Несколько строк | Разбор инцидента с отбрасыванием валидных планов у части клиентов |
| И-4 блокировки циклов | Обёртка вокруг цикла | Гонки и дублирование операций над флотом |
| И-6 лимиты в базе | Запрос вместо счётчика | Тихо отключённая защита от перебора |
| И-10 конверт транспорта | Один уровень вложенности | Изменение схемы плана у всех клиентов сразу |
| И-11 capability negotiation | Одно поле в запросе | Невозможность выкатить транспорт постепенно |
| И-14 адаптер транспорта | Один интерфейс | Переписывание клиента |
| И-15 `transport_kind` | Одно поле | Отсутствие данных для решения именно тогда, когда оно срочно |

Все инварианты этого документа стоят сегодня меньше дня работы суммарно. Ни один из них не оправдывает усложнения MVP, потому что ни один не добавляет компонента — все они про форму кода и схемы, а не про количество движущихся частей.
