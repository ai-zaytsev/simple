# MVP sizing: принятые ограничения

Это история sizing-решений, а не живой инвентарь. Текущие хосты, провайдеры, регионы, состояние и действия при росте находятся только в [операционной инструкции Business Owner](../business-owner-operations.md).

## Почему Core и PostgreSQL совмещены

На стартовой нагрузке Go Core и PostgreSQL помещаются на одном малом сервере. Отдельный DB-host увеличил бы постоянную стоимость и число отказов без измеримой пользы. Цена компромисса:

- Core и БД имеют общий host failure domain;
- ресурсные метрики хоста до отдельного monitoring agent проверяются вручную;
- перенос БД допустим только после появления и проверки backup/restore.

Состояние обязано жить в PostgreSQL, а не в памяти Core или случайных локальных файлах. Поэтому resize или перенос Core не должен требовать изменения Android.

## Почему нет отдельного observability-host

ClickHouse, Loki, Prometheus и Grafana не развёрнуты. На стартовых объёмах продуктовые метрики и агрегаты помещаются в PostgreSQL, панель отдаёт Core, а журналы остаются в journald. Отдельный стек вводится только при измеримом триггере из [deferred-stack-migration.md](deferred-stack-migration.md), а не потому, что он присутствовал в ранней схеме.

Это решение не означает, что текущая наблюдаемость полна: host monitoring Core/DB и APK site отсутствует, а журналы не архивируются. Эти пробелы открыто записаны в [tech-debt.md](../tech-debt.md).

## Почему VPN-ноды расходуемые

Блокировка IP/домена — ожидаемый failure mode. Нода не восстанавливается как уникальный сервер: новая создаётся штатным workflow, проверяется с Core и Android, входит в выдачу, старая выводится. Увеличение размера заблокированной ноды не помогает.

При малом fleet progressive disclosure имеет ограниченную эффективность: один connection plan может раскрыть значительную часть доступных нод. Механизм assignment остаётся нужен для роста, но стартовая защита — быстрая замена и запас доменов.

## Почему APK site отдельный

Публичный домен загрузки и крупные APK не разделяют process и диск с Core. Малый stateless origin проксирует immutable artifacts из object storage; его можно пересоздать без потери истории релизов. Решение о конкретном placement и текущий статус `site-1` находятся в BO-инструкции.

## Границы бюджета

- autoscaling платных ресурсов запрещён;
- новый постоянный сервер создаётся только после измерения узкого места и решения Business Owner;
- трафик проверяется по фактическому bill/usage провайдера, а не по старым прайс-листам в repository;
- месячная квота FREE сейчас не реализована, поэтому старый расчёт на 20 ГиБ нельзя считать действующим продуктовым лимитом;
- после любого resize/add/remove сверяются live panel, provider inventory и bill.

Точные пороги и последовательности для пользователей, соединений, трафика, Core, PostgreSQL и VPN-ноды находятся в [разделе роста нагрузки](../business-owner-operations.md#рост-нагрузки).

## Неиспользуемый сервер `ru`

Ранний план предполагал отдельный probe в России. Фактические проверки доступности выполняются Android-устройствами из целевой сети, поэтому `ru` не участвует в runtime и не должен учитываться как резерв Core или VPN-нода. Решение о его выключении/удалении является отдельным действием Business Owner; этот документ его не авторизует.
