# Android Client

Устройство клиента и то, как в нём выполняются требования Стадии 2.

Код: [`android/`](../../android). Сборка только в CI: на машине разработчика нет ни JDK, ни Android SDK, ни Go.

## Границы Ответственности

```
MainActivity          только отображение и намерения
   |
VpnController         состояние на уровне процесса
   |
SimpleVpnService      владеет туннелем
   |-- TunConfigurator     создаёт TUN, исключает приложения
   |-- NetworkMonitor      смена Wi-Fi и мобильной сети
   |-- XrayConfigBuilder   конфигурация движка
   |-- XrayEngine          единственное место, знающее про Xray
```

Состояние живёт в `VpnController`, а не во `ViewModel`. Причина прямая: `ViewModel` умирает вместе с Activity, а туннель — нет. Закрытие экрана не должно влиять на соединение, поэтому владение состоянием вынесено на уровень процесса, а владение туннелем — в сервис.

`XrayEngine` — единственный тип, за которым известно, что транспорт это Xray, протокол VLESS, а маскировка REALITY. Это инвариант И-14 из [evolution.md](evolution.md): второй транспорт не должен затрагивать ни UI, ни контроллер сессии.

## Как Закрываются Критерии Приёмки

| Критерий | Чем обеспечен |
| --- | --- |
| ON устанавливает VPN | `MainActivity` запрашивает системное согласие, сервис поднимает TUN и стартует движок |
| OFF корректно выключает | `teardown()` останавливает движок, закрывает дескриптор, снимает foreground |
| Нет VPN loop | Приложение исключает само себя из туннеля |
| Нет очевидного DNS leak | DNS выдаётся внутрь туннеля, проксируемые имена резолвятся удалённо по DoH |
| Ошибка Xray не роняет приложение | Старт обёрнут в перехват `Throwable`, отказ движка это состояние `Failed`, а не исключение |
| Закрытие Activity не ломает работу | Туннель в foreground-сервисе, состояние в объекте уровня процесса |
| Переход Wi-Fi и мобильной сети | `NetworkMonitor` перезапускает движок при смене нижележащей сети |
| Воспроизводимая сборка | Всё зафиксировано, см. раздел ниже |

### Почему приложение исключает само себя

Пакеты, которые движок отправляет на VPN-сервер, сами попадают в TUN, если приложение не исключено. Оттуда они возвращаются в движок, тот снова отправляет их наружу — и туннель выглядит зависшим.

`addDisallowedApplication(packageName)` разрывает цикл точно и без исключений в маршрутизации. Если этот вызов не проходит, `TunConfigurator` бросает исключение вместо того, чтобы продолжить: молча поднятый зацикленный туннель хуже, чем несостоявшееся подключение.

### Почему IPv6 забирается в туннель

Если не заявить IPv6, устройство с рабочим IPv6 пойдёт мимо туннеля, пока пользователь считает себя защищённым. Поэтому маршрут `::/0` заявляется всегда: IPv6 либо идёт через туннель, либо не работает. Заметный отказ лучше незаметной утечки.

### Почему access log выключен в генераторе

`XrayConfigBuilder` — единственное место, где рождается конфигурация движка, и он всегда ставит `access: none`. Access log содержит каждый адрес назначения, то есть ровно ту историю посещений, которую запрещает [privacy-model.md](privacy-model.md). Запрет реализован в генераторе, а не в настройках по умолчанию, поэтому включить его в рантайме нечем.

## Умная Маршрутизация

Требование: всё, что требует российского адреса, идёт напрямую, остальное через прокси, и пользователь ничего не выбирает.

Одного механизма недостаточно, поэтому их два.

**Уровень ОС: исключение приложений.** Банковские и государственные приложения проверяют адрес выхода, а иногда и пиннят сертификаты. Они обращаются к множеству хостов, и маршрутизация по доменам для них ненадёжна. Исключение приложения целиком точно и не зависит от того, куда именно оно ходит.

**Уровень движка: маршрутизация по адресам и именам.** `geoip:ru` и `geoip:private` идут напрямую. Список российских доменов идёт напрямую по имени, потому что российский сервис за иностранным CDN по адресу выглядит иностранным.

Чтобы правило по имени срабатывало, во входящем соединении включён sniffing: имя хоста восстанавливается из потока, и маршрут выбирается по имени, а не только по адресу.

**Оба списка — данные, а не код.** Сейчас они лежат в `RoutingPolicy.DEFAULT`, в готовом продукте приходят из Control Plane и меняются без релиза приложения. Стартовый список намеренно короткий: длинный список, составленный по памяти, создаёт ложную уверенность. Каждая запись должна появляться из наблюдения.

Ограничение уровня ОС: набор исключённых приложений фиксируется в момент создания TUN. Изменение списка требует пересоздания туннеля, то есть переподключения.

## DNS

- TUN объявляет DNS-адрес внутри туннеля, поэтому системные запросы не уходят мимо
- проксируемые имена резолвятся удалённо по DoH: локальный резолвер не видит, куда ходит пользователь
- имена из списка прямого доступа резолвятся локально намеренно: эти сервисы должны видеть российский адрес, и резолвинг за границей ломает разделение

## Воспроизводимость Сборки

Что зафиксировано:

- версии Gradle, AGP, Kotlin и всех зависимостей заданы явно в каталоге версий, диапазонов нет
- JDK и версия Gradle закреплены в workflow
- `dependenciesInfo` выключен: без этого в APK попадает блок, зависящий от машины сборки
- в репозитории нет бинарника gradle wrapper: версия Gradle задаётся в CI, а не JAR-файлом в истории
- SHA-256 артефакта печатается в отчёт сборки

Чего это ещё не даёт: побитовой идентичности релизных APK. Для неё нужен фиксированный контур подписи и устранение временных меток в архиве. Отладочная сборка воспроизводима в смысле «тот же коммит и тот же тулчейн дают ту же функциональность», и это честная формулировка текущего состояния.

## Что В Слайсе Временно

**Профиль подключения читается из ассета, а не из подписанного плана.** Control Plane ещё нет. Ассет не хранится в репозитории: он содержит рабочий credential и адрес ноды. Сборка без него даёт приложение, которое честно сообщает, что endpoint не настроен.

Весь этот путь собран в одном файле `SliceProfileSource`, чтобы его исчезновение было удалением файла, а не рефакторингом. Это единственное место, где клиент держит конфигурацию, которую не получил от сервера, то есть единственное нарушение `ADR-001`, и оно ограничено сроком жизни слайса.

**Движок ещё не привязан.** `PendingXrayEngine` отказывается стартовать и говорит почему. Он намеренно не притворяется успешным: сборка, сообщающая о работающем туннеле без туннеля, устраивает интерфейс и обманывает пользователя.

Привязка пишется после того, как workflow `libXray Build` соберёт AAR и напечатает его фактическую публичную сигнатуру. Писать её по памяти означает получить либо несобирающийся код, либо, что хуже, собирающийся и неверный.
