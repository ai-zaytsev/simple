## Расчёт На 50 Пользователей

Лимит FREE: 20 ГиБ в месяц и 20 Мбит/с на пользователя.

**Трафик.** 50 × 20 ГиБ = 1 ТБ в месяц, если каждый выберет квоту полностью. Включено 5 ТБ. Запас пятикратный, и это при нереалистичном допущении, что квоту выбирают все.

**Полоса.** При одновременности 25 % это 13 активных. Если бы все тринадцать держали свои 20 Мбит/с непрерывно — 260 Мбит/с. Реально просмотр страниц даёт в среднем 0,5–2 Мбит/с на активного, то есть 7–26 Мбит/с. Пиковые всплески короткие.

**Процессор.** Одно ядро с аппаратным AES проксирует порядка 200–400 Мбит/с TLS. На указанной полосе не напрягается.

**Вывод: одна нода Basic несёт 50 пользователей с большим запасом.**

## Сколько Нод Всё-Таки Брать

Одной мало, и не по нагрузке.

План подключения по построению содержит **основную ноду и два резерва** — см. [remote-config.md](remote-config.md). При одной ноде резервы не существуют, и любая её потеря оставляет пользователей без связи до вмешательства вручную.

| Вариант | Стоимость | Что даёт |
| --- | --- | --- |
| 1 нода | $4/мес | нагрузку держит, отказ не переживает |
| **2 ноды** | **$8/мес** | реальный резерв, план с непустым `reserves` |
| 3 ноды | $12/мес | полный план по схеме, запас на замену одной |

**Рекомендация на первый месяц: две ноды, $8/мес.** Третья добавляется, когда появятся платящие пользователи, а не по числу активных.

## Порог Добавления Следующей Ноды

По измерению, а не по числу пользователей. Считать надо то, что действительно ограничивает.

Добавлять ноду, когда выполняется любое из:

- средняя загрузка ядра выше **60 %** в течение часа в пике
- исходящая полоса выше **60 %** от измеренной пропускной способности ноды в течение часа
- израсходовано больше **3,5 ТБ** из пятитерабайтного пакета до 20-го числа месяца
- время установления туннеля в телеметрии выросло вдвое против недельной медианы

Первые три — про запас. Четвёртый — про то, что пользователь уже чувствует.

Оценочно один Basic держит **150–200 пользователей** при тех же допущениях. Число это расчётное: ни одна нода под настоящей нагрузкой ещё не измерялась, и до первых сотен пользователей его надо подтвердить, а не принимать на веру.

## Что Масштабирование Не Должно Задевать

Ноды создаются и удаляются **через API их собственного провайдера, из конвейера**. Control Plane в этом не участвует: он публикует, какие ноды существуют, но не создаёт их.

Следствие: при недоступности Control Plane ноду всё равно можно добавить или заменить. Клиенты узнают о ней, когда Control Plane вернётся. Обратная схема — когда флот масштабируется из Core — сделала бы недоступность Core ещё и невозможностью чинить ноды.
