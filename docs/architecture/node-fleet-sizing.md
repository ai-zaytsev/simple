# Размер флота нод: модель

Это техническая модель факторов ёмкости, не live inventory и не прайс-лист. Текущие ноды, provider bill, capacity verdict, пороги и Add/Retire procedure находятся только в [BO-инструкции](../business-owner-operations.md#растёт-число-vpn-соединений).

## Что ограничивает ноду

| Ограничение | Как проявляется |
| --- | --- |
| Полоса | Растут latency/loss, пользовательская скорость и throughput перестают масштабироваться |
| CPU | TLS в Nginx и обработка Xray упираются в ядро |
| Provider traffic package | Растёт bill или приближается лимит периода |
| Память | Xray/Nginx/agents приближаются к безопасному запасу |
| Число соединений из конфигурации | Core перестаёт считать ноду свободной независимо от железа |
| Блокировка IP/домена | Нода может быть пустой по ресурсам, но непригодной из целевой сети |

Последний пункт принципиален: блокированную ноду заменяют, а не увеличивают.

## Почему минимум больше одной ноды

Одна машина может выдерживать стартовую нагрузку, но не переживает provider failure, блокировку или maintenance. Нужны одновременно:

- serving capacity для текущих сессий;
- хотя бы один проверенный резерв;
- готовые расходные домены, иначе новую ноду нельзя ввести;
- независимые проверки от Core и Android в целевой сети.

Connection plan может содержать primary и reserves, но приложение не создаёт резерв, если его нет во fleet. Поэтому решение о размере пула принимается по capacity/spares/endpoint health вместе, а не только по числу пользователей.

## Расчёт до измерений

Для приблизительной оценки нужны:

1. пиковые одновременные соединения, а не регистрации;
2. реальный средний и P95 throughput активной сессии;
3. измеренная пропускная способность выбранного provider path;
4. CPU/memory/latency/loss конкретной ноды;
5. месячный provider traffic и bill.

Старая модель исходила из 50 пользователей, 25% одновременности и квоты FREE 20 GiB. Квота не была утверждена как действующий лимит и не реализована, поэтому этот расчёт нельзя использовать для текущего capacity или бюджета. До накопления production history panel считает capacity в соединениях; перевод в пользователей остаётся оценочным.

## Технический инвариант масштабирования

Ноды создаются и удаляются через provider API из GitHub Actions. Core регистрирует, проверяет и выдаёт их, но не создаёт платные machines автоматически. Последовательность:

    измеримый SCALE_REQUIRED
      → готовый расходный домен
      → Add Server
      → heartbeat и Node Inspect
      → Android connectivity/privacy check
      → serving
      → повторный panel/provider/bill readback

Пороговые числа не копируются сюда: они меняются вместе с серверной capacity policy и перечислены в BO-инструкции.
