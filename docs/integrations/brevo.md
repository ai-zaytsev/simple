# Brevo — Email Provider

Провайдер транзакционной почты для magic link. Решение зафиксировано в `ADR-012`, см. [../architecture/decisions.md](../architecture/decisions.md).

Панель: `app.brevo.com`. API: `https://api.brevo.com/v3`.

## Роль В Системе

Единственная функция — доставка письма с magic link. Ничего больше через провайдера не проходит: ни маркетинговых рассылок, ни уведомлений, ни данных о трафике.

Это делает Brevo компонентом, отказ которого блокирует **вход новых пользователей целиком**, но не влияет ни на существующие туннели, ни на связность, см. [../architecture/failure-scenarios.md](../architecture/failure-scenarios.md).

## Секреты

| Имя | Что это | Где задаётся |
| --- | --- | --- |
| `BREVO_API_KEY` | API-ключ v3, формат `xkeysib-...` | GitHub Secrets, позже — secrets store Control Plane |
| `BREVO_SENDER_EMAIL` | Адрес отправителя на подтверждённом домене | GitHub Secrets |
| `EMAIL_TEST_RECIPIENT` | Адрес для проверочных писем | GitHub Secrets |

Задать или обновить:

```bash
gh secret set BREVO_API_KEY --repo ai-zaytsev/simple
```

Команда запросит значение в интерактивном режиме и не оставит его в истории оболочки. Обновление ключа — та же команда: она перезаписывает значение.

Почему `BREVO_SENDER_EMAIL` и `EMAIL_TEST_RECIPIENT` тоже секреты, хотя это не ключи: репозиторий публичный, а всё, что попадает в переменные и в логи Actions, видно всем. Адрес отправителя, оказавшийся в открытом доступе, немедленно собирается спам-ботами.

## Требования К Домену Отправителя

Без этого письма будут уходить в спам у российских почтовых сервисов, и продукт не заработает независимо от качества остального кода:

| Запись | Зачем |
| --- | --- |
| SPF | Разрешает Brevo отправлять от имени домена |
| DKIM | Подпись, без которой `mail.ru` и `yandex` резко понижают доверие |
| DMARC | Политика обработки писем, не прошедших проверку |
| Verified sender | Домен подтверждён в панели Brevo |

Отдельный поддомен для транзакционной почты предпочтителен: репутация транзакционных писем не смешивается с остальной почтой домена.

## Проверка

Workflow `Email Provider Check`, ручной запуск:

```bash
gh workflow run email-provider-check.yml --repo ai-zaytsev/simple
```

Что делает:

1. Проверяет наличие секретов.
2. `GET /v3/account` — валидность ключа.
3. `POST /v3/smtp/email` — отправляет тестовое письмо на `EMAIL_TEST_RECIPIENT`.
4. `GET /v3/smtp/statistics/events` — опрашивает события по `messageId` с несколькими попытками.

Чего workflow не делает и не может: определить, попало письмо во «Входящие» или в спам. Это проверяется глазами, и это главная проверка. Провайдер, чьи письма стабильно уходят в спам у `mail.ru` и `yandex`, не подходит, каким бы зелёным ни был статус API.

Ни ключ, ни адреса, ни данные аккаунта в логи не печатаются.

## Что Использует Control Plane

| Операция | Endpoint | Когда |
| --- | --- | --- |
| Отправка magic link | `POST /v3/smtp/email` | На каждый запрос входа |
| Приём событий доставки | Webhook от Brevo | Опционально, для метрики доставляемости |

Заголовок авторизации: `api-key: <BREVO_API_KEY>`.

Требования к письму magic link:

- только `textContent` и минимальный HTML: тяжёлые шаблоны повышают вероятность попадания в спам
- ссылка одноразовая, TTL 15 минут, см. [../architecture/remote-config.md](../architecture/remote-config.md)
- в письме нет ничего, кроме ссылки и пояснения: ни VPN-параметров, ни идентификаторов
- адрес получателя не попадает в логи Control Plane, см. [../architecture/privacy-model.md](../architecture/privacy-model.md)

## Ограничения И Риски

| Риск | Реакция |
| --- | --- |
| Письма уходят в спам | Настройка DKIM/SPF/DMARC, прогрев домена, при неуспехе — смена провайдера |
| Лимит отправок на плане исчерпан | Мониторинг остатка, алерт заранее |
| Провайдер недоступен | Переключение на резервного, см. ниже |
| Ключ скомпрометирован | Отзыв в панели Brevo, выпуск нового, обновление секрета |

## Резервный Провайдер

Не выбран. По `ADR-012` он обязателен и настраивается **заранее как конфигурация**, а не подключается в момент инцидента: во время отказа основного провайдера вход новых пользователей закрыт полностью, и в этот момент интеграцию не пишут.

Требование к архитектуре Control Plane: отправка письма выполняется через интерфейс с выбором провайдера в конфигурации, а не через прямой вызов Brevo из кода авторизации.
