# Brevo — Email Provider

Провайдер транзакционной почты для magic link. Решение зафиксировано в `ADR-012`, см. [../architecture/decisions.md](../architecture/decisions.md).

Панель: `app.brevo.com`. API: `https://api.brevo.com/v3`. Авторизация: заголовок `api-key`.

## Роль В Системе

Две функции: письмо с magic link и предупреждения о мощности, которые идут нам, а не пользователю. Больше через провайдера не проходит ничего: ни маркетинговых рассылок, ни данных о трафике.

**Brevo только отправляет.** Ящиков у него нет, входящую почту он не принимает и не пересылает. Приём на `simple-vpn.download` идёт через Cloudflare Email Routing — это отдельная система, и путать её с отправкой дорого: `support@` и `admin@` заводятся там, а не здесь.

**Адрес для алертов не должен жить на нашем домене.** Предупреждение о том, что с инфраструктурой плохо, не может ехать через ту же инфраструктуру: письмо о поломке Cloudflare, идущее через Cloudflare Email Routing на нашей зоне, — это сигнал, зависящий от того, о чём он сигналит. Поэтому `CP_ALERT_EMAIL` — почта, не связанная с проектом.

Отказ провайдера блокирует **вход новых пользователей целиком**, но не влияет ни на существующие туннели, ни на связность, см. [../architecture/failure-scenarios.md](../architecture/failure-scenarios.md).

## Конфигурация

| Имя | Тип | Что это |
| --- | --- | --- |
| `BREVO_API_KEY` | Secret | API-ключ v3 |
| `EMAIL_TEST_GMAIL` | Secret | Проверочный ящик Gmail |
| `EMAIL_TEST_YANDEX` | Secret | Проверочный ящик Yandex |
| `BREVO_SENDER_EMAIL` | Variable | Адрес отправителя |
| `CP_REPLY_TO` | Variable | Куда уходит ответ на наше письмо |
| `CP_ALERT_EMAIL` | Secret | Куда приходят предупреждения о мощности |

Задать или обновить ключ — интерактивно, чтобы значение не осталось в истории оболочки:

```bash
gh secret set BREVO_API_KEY --repo ai-zaytsev/simple
```

Почему проверочные ящики — секреты, а адрес отправителя — переменная: репозиторий публичный, логи Actions видны всем. Адреса получателей не должны попадать в вывод ни при каких обстоятельствах. Адрес отправителя и так виден в заголовках каждого письма, но в логи он тоже не печатается.

## Отслеживание Открытий И Переходов

Для писем с magic link отслеживание должно быть выключено. Причины две: приватность и доставляемость — переписанная ссылка на трекинговом домене выглядит для почтового фильтра хуже, чем прямая ссылка на домен сервиса.

Как это обеспечивается:

1. **Письмо отправляется только как `textContent`, без HTML.** Пиксель отслеживания открытий вставляется в HTML и в текстовом письме существовать не может.
2. **Отслеживание переходов выключается в настройках аккаунта Brevo** для транзакционной почты. Это настройка панели, а не параметр запроса.
3. **Проверка — эмпирическая.** В проверочном письме есть ссылка-образец вида `https://simple-vpn.download/auth/verify?token=probe-...`. В полученном письме она должна остаться неизменной. Если она переписана на домен провайдера — отслеживание переходов включено, и его нужно выключить в панели.

Третий пункт важнее первых двух: он проверяет фактическое поведение, а не заявленную настройку.

## Проверка Доставляемости

Workflow `Email Provider Check`, ручной запуск:

```bash
gh workflow run email-provider-check.yml --repo ai-zaytsev/simple
```

Что делает:

1. Проверяет наличие секретов и переменной.
2. `GET /v3/account` — валидность ключа, тип плана, остаток кредитов.
3. `POST /v3/smtp/email` — отправляет по письму на каждый проверочный ящик, plain text, с меткой `deliverability-check`.
4. `GET /v3/smtp/statistics/events` — опрашивает события по каждому `messageId` с несколькими попытками.
5. Печатает `messageId` и события в summary, обозначая получателей классами `gmail` и `yandex`.

Чего workflow не делает и не может: определить, попало письмо во «Входящие» или в спам. Это проверяется человеком, и это главная проверка. Валидный ключ и `HTTP 201` о доставляемости не говорят ничего.

## Webhook Доставки

Не настроен: требует публичного HTTPS-эндпоинта, которого пока нет. Ниже — контракт, который реализует Control Plane.

**Эндпоинт:** `POST /v1/webhooks/email/{secret-path}`

**События:** `delivered`, `softBounce`, `hardBounce`, `blocked`, `error`, `spam`.

**Аутентификация.** Brevo не подписывает webhook-запросы, поэтому доверять телу нельзя. Три рубежа:

1. неугадываемый сегмент пути, хранящийся как секрет
2. сверка `message-id` из тела с нашей записью об отправленном письме: событие о письме, которого мы не отправляли, отбрасывается
3. идемпотентность по паре `message-id` и `event`: повторная доставка того же события не меняет состояние

**Приватность.** Тело события содержит адрес получателя. Обработчик:

- сопоставляет адрес с `account_id` и дальше работает только с ним
- не пишет адрес ни в логи, ни в аналитику, см. [../architecture/privacy-model.md](../architecture/privacy-model.md)
- в метрики отдаёт только класс почтового провайдера, выведенный из домена: `gmail`, `yandex`, `mailru`, `other`. Это низкокардинальный признак, а не идентификатор

Класс провайдера даёт то, что нужно бизнесу: видно, если письма перестали доходить конкретно до `mail.ru`, при этом ни один адрес не сохраняется.

**Реакция на события:**

| Событие | Действие |
| --- | --- |
| `delivered` | Счётчик доставленных, метрика по классу провайдера |
| `softBounce` | Временная проблема: повторная отправка разрешена, счётчик растёт |
| `hardBounce` | Адрес помечается недоставляемым, отправка прекращается, пользователю на следующей попытке входа показывается понятная причина |
| `blocked` | То же, что `hardBounce`, но причина — блок-лист провайдера; требует разбора |
| `error` | Алерт эксплуатации |
| `spam` | Жалоба на транзакционное письмо: отправка на адрес прекращается, случай разбирается вручную |

## Требования К Письму Magic Link

- только `textContent`, без HTML
- в письме нет ничего, кроме ссылки и короткого пояснения: ни VPN-параметров, ни идентификаторов, ни данных аккаунта
- ссылка одноразовая, TTL 15 минут
- адрес получателя не попадает в логи Control Plane

## Ограничения И Риски

| Риск | Реакция |
| --- | --- |
| Письма уходят в спам | Прогрев домена, контроль репутации, при неуспехе — смена провайдера |
| Лимит отправок на плане исчерпан | Мониторинг остатка кредитов, алерт заранее |
| Провайдер недоступен | Переключение на резервного |
| Ключ скомпрометирован | Отзыв в панели, выпуск нового, обновление секрета |
| Отслеживание переходов включено | Проверка ссылки в полученном письме, отключение в панели |

## Резервный Провайдер

Не выбран. По `ADR-012` обязателен и настраивается **заранее как конфигурация**, а не подключается в момент инцидента: во время отказа основного провайдера вход новых пользователей закрыт полностью, и в этот момент интеграцию не пишут.

Требование к Control Plane: отправка письма выполняется через интерфейс с выбором провайдера в конфигурации, а не прямым вызовом Brevo из кода авторизации.
