# DNS

Управление DNS для инфраструктуры MVP. Два независимых провайдера, разные роли доменов, автоматизация через GitHub Actions.

## Провайдеры

| Провайдер | API | Аутентификация | Права токена |
| --- | --- | --- | --- |
| Cloudflare | `https://api.cloudflare.com/client/v4` | `Authorization: Bearer` | DNS Write, ограничен доменами проекта |
| Spaceship | `https://spaceship.dev/api/v1` | `X-API-Key` + `X-API-Secret` | DNS Records Read, DNS Records Write |

Секреты: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `SPACESHIP_API_KEY`, `SPACESHIP_API_SECRET`.

Два провайдера — не избыточность ради избыточности. Из [../architecture/bootstrap-recovery.md](../architecture/bootstrap-recovery.md): точки входа обязаны быть независимыми. Четыре домена под управлением одного DNS-провайдера — это одна точка отказа, а не четыре.

Ни один токен не имеет прав на регистрацию, продление или трансфер доменов. Это осознанно: автоматизация меняет записи, но не может потерять домен.

## Роли Доменов

| Роль | Переменная | Что это | Публичность |
| --- | --- | --- | --- |
| `control-plane` | константа workflow | Стабильное имя Core | Публично и входит в seed APK |
| `vpn-entry` | `VPN_ENTRY_DOMAINS` | Расходный домен cover, VPN и edge к Core | Публичен после ввода; запас до ввода не должен рекламироваться клиенту |
| `site` | `SITE_DOMAIN` | Сайт для скачивания APK и почтовый поддомен | Публичен, рекламируется |

Домены хранятся в repository variables, а не в секретах: маскировать их бессмысленно, потому что они и так уезжают в каждую установку приложения. Из [../architecture/threat-model.md](../architecture/threat-model.md): неизвестность домена не является security boundary.

### Почему сайт и точки входа разделены

Домен сайта рекламируется, значит будет заблокирован в России раньше всех остальных. Если бы API Control Plane жил на нём, блокировка сайта убивала бы сервис целиком. Поэтому:

- на `SITE_DOMAIN` не размещается ни один endpoint Control Plane
- `SITE_DOMAIN` не входит в bootstrap descriptor
- блокировка сайта означает только то, что новую сборку сложнее скачать, и не влияет на работу установленных приложений

## Правило, Нарушение Которого Ломает Всё

**Cloudflare proxy для `vpn-entry` записей должен быть выключен.** Оранжевое облако терминирует TLS на стороне Cloudflare. Для основного VLESS over WebSocket/TLS это означает полную неработоспособность сквозного туннеля к Xray.

Это самая вероятная операционная ошибка во всей DNS-части, потому что проксирование включается по умолчанию при создании записи через панель Cloudflare.

Workflow `DNS Inventory` проверяет это на каждом запуске и падает, если находит проксированную запись на домене с ролью `vpn-entry`.

## Конвенции Записей

| Запись | Назначение | TTL | Примечание |
| --- | --- | --- | --- |
| `A` на apex `vpn-entry` домена | Адрес Core или edge-ноды | Низкий, 300 с | Низкий TTL нужен для быстрой ротации |
| `A` на `SITE_DOMAIN` | Хостинг сайта с APK | Обычный | Ротация не требуется |
| `TXT`, `CNAME` на `mail.SITE_DOMAIN` | SPF, DKIM, DMARC для Brevo | Обычный | См. [brevo.md](brevo.md) |
| `CAA` | Ограничение выпуска сертификатов | Обычный | Опционально |

Низкий TTL на точках входа — часть модели расходуемости: замена IP не должна ждать истечения кэша у резолверов.

## Текущее Состояние

Актуальные домены, регистраторы, DNS-провайдеры, роли и пригодность запаса находятся только в [BO-инструкции](../business-owner-operations.md#домены). Живые записи читает `DNS Inventory`; его снимок важнее документации.

Приём почты и отправка остаются разными контурами: MX обслуживает Cloudflare Email Routing, а Brevo только отправляет.

## Особенность Cloudflare-токена

Токен возвращает `HTTP 401` на `GET /user/tokens/verify` и при этом штатно работает с `GET /zones` и записями. Это не сломанный токен: эндпоинт `user/tokens/verify` требует права читать метаданные самого токена, а выданный токен ограничен зонами и DNS.

Отсюда правило для любых будущих проверок: **работоспособность Cloudflare-токена проверяется обращением к `zones`, а не к `user/tokens/verify`.** Проверка через `verify` даёт ложноотрицательный результат на правильно суженном токене, то есть наказывает за корректное ограничение прав.

## Workflow

`DNS Inventory`, ручной запуск, ничего не изменяет:

```bash
gh workflow run dns-inventory.yml --repo ai-zaytsev/simple
```

Отвечает на четыре вопроса:

1. Работают ли учётные данные обоих провайдеров.
2. Какой провайдер обслуживает стабильный Core, сайт и каждый расходный домен.
3. Какие записи и роли видит автоматизация.
4. Нет ли проксирования Cloudflare на `vpn-entry` доменах.

Токены и идентификатор аккаунта в логи не печатаются. Имена доменов печатаются: они публичны по построению.

## Замечание По Именам Доменов

Текущие `vpn-entry` домены образуют распознаваемый шаблон: пары соседних чисел в одной зоне `.xyz`. Противник, узнавший один домен, угадывает остальные простым перебором соседних значений.

Из [../architecture/bootstrap-recovery.md](../architecture/bootstrap-recovery.md): четыре точки входа с общим признаком — это одна точка входа. Для MVP текущий набор рабочий, но при следующей закупке доменов шаблона нужно избегать: несвязанные имена, разные TLD, разные регистраторы.

Уточнение к «публичны по построению». Certificate Transparency публикует имя в момент выпуска сертификата, то есть когда домен уже введён в работу. Публичный репозиторий публикует и **неиспользованный резерв** — до того, как он понадобится. Это разные вещи: противник получает не текущую точку входа, а список будущих. Пока резерв мал и одноразов, цена низкая; при переходе к настоящей ротации доменов список запаса в репозитории держать нельзя.

## Что Автоматизация Делать Не Будет

- регистрировать, продлевать и переносить домены
- менять nameservers
- трогать записи, не относящиеся к ролям выше
- включать Cloudflare proxy на `vpn-entry` записях

## Постоянные Правила Ролей

- стабильное имя Core не переносится на расходный домен;
- сайт скачивания не совмещается с выдачей конфигурации;
- расходные домены распределяются между независимыми регистраторами/DNS;
- фактическое сопоставление домен → роль не копируется сюда и читается в [BO-инструкции](../business-owner-operations.md#домены).

## Техническое Правило Deploy Сайта

`Deploy APK Site` создаёт или обновляет только одну apex `A`-запись. Сначала proxy выключен, чтобы `site-1` получил Let's Encrypt certificate по HTTP-01. После успешного внешнего HTTPS workflow включает Cloudflare proxy и ещё раз читает страницу. Это правило относится только к `site`: запрет proxy для `vpn-entry` остаётся без исключений.
