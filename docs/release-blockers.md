# Блокеры Релиза

Список того, что **обязано** быть сделано до выкатки. Не «желательно», не «когда дойдут руки»: пока здесь есть незакрытый пункт, релиза не будет.

Отдельный документ, а не строчка в задачах фичи, потому что задачи фичи закрываются вместе с фичей, а эти пункты переживают её и должны попадаться на глаза.

Открытый пункт здесь останавливает `Publish APK` — это не напоминание, а
работающий гейт. Единственное исключение — пункт про саму первую публикацию:
он закрывается тем самым запуском, который иначе отказывался бы стартовать.
Исключение сделано по имени и проверяется `.github/scripts/check-release-blockers.sh`.

Закрытые пункты остаются внизу вместе с доказательствами. Удалённый пункт
через месяц выглядит как пункт, которого не было, и его ищут заново.

## Закрытые

Держатся здесь, а не удаляются: закрытый пункт объясняет, почему такого больше
не ищут, и чем именно это было доказано.


## Первая Официальная APK Не Опубликована

**Статус:** закрыт 2026-09-01. Заведён 2026-08-31 при полной инвентаризации.

Публикация `0.1.0 (versionCode 1)` выполнена штатным `Publish APK` из `main`.

**Доказательства по официальному домену**, прочитанные напрямую, а не из лога запуска:

- `/releases.json`: `latest = 0.1.0`, versionCode 1, `publishedAt 2026-09-01T13:43:57Z`, commit `54a2d5a`;
- `/download/latest.apk`: HTTP 200, 56 599 049 байт, SHA-256 `e99ce3d92aa61f7aaf24897a1ee550ffdc206ce97ef75bb7696431befc126165` — совпадает с манифестом;
- `/download/releases/0.1.0/simple-vpn-0.1.0.apk`: HTTP 200;
- сертификат подписи `38dfe1cd022b3845bb696f841fcf729c623995407e8fc1f27b013b358499da64`, прочитан дважды: у собранного артефакта до загрузки и у публичной копии после;
- `Core latest now names the publicly verified immutable APK` — релиз зарегистрирован каналом `direct_apk`;
- панель: последняя `0.1.0 (1)`, **каналов с артефактом 1** (было 0).

**Живая приёмка пути пользователя.** Business Owner прошёл с телефона весь путь, ради которого делалась стадия: открыл `simple-vpn.download`, скачал APK, установил по инструкции на странице и вошёл в приложение. Инструкция совпала с тем, что показывал телефон, на всех шагах.

**Что стоило двух неудачных запусков.** Первый остановился до единой загрузки: чтение отпечатка сертификата было привязано к формату `Signer #1 …`, который нынешние build-tools не печатают. Второй загрузил всё и упал на публичной проверке — той же ошибкой во **второй копии** того же разбора. Дефектом были не буквы шаблона, а две копии одного правила; теперь чтение живёт в `.github/scripts/apk-certificate.sh` и вызывается обоими шагами.

Ни один из отказов не оставил половинчатого состояния: проверка стоит до первой записи, а повторный запуск отказывается перезаписывать неизменяемые байты и продолжает как синхронизация с Core.
## VIP Ни Разу Не Исполнялся

**Статус:** закрыт 2026-08-29 — в тот же день, когда был заведён.

Причина, по которой он вообще появился: VIP-аккаунтов было ноль, политика была
записана в строках базы, но **ни один путь VIP никогда не выполнялся**. Из-за
этого висела приёмка стадий 21, 22 и 23.

Мешало не отсутствие решения, а отсутствие безопасного способа назначить тариф:
`SetAccountTier` работает по email-адресу, а входные параметры
`workflow_dispatch` попадают в публичный заголовок запуска.

**Чем закрыт.** Заведено назначение тарифа по **префиксу идентификатора**
аккаунта — ручке, которую можно печатать в публичном логе, — с отказом на
неоднозначном префиксе. После этого VIP был назначен и путь пройден целиком на
живом устройстве Business Owner:

- тариф назначен, панель показала `VIP | 1 аккаунт` из строк базы;
- ограничение скорости снято — замер показал больше 10 Мбит/с;
- внешнее устройство добавлено и удалено;
- **ссылка вставлена в сторонний клиент на другом устройстве и заработала.**

Последнее и есть настоящая приёмка стадии 22: доступ, выданный не нашему
приложению, оказался живым.

## Путь Входа Один И Не Проверен Оттуда, Откуда Важно

**Статус:** закрыт 2026-08-30. Обнаружено 2026-08-29, причина найдена и исправлена 2026-08-30.

```
| №4 | путь входа | works | отсюда 100% | с устройств — | проверок 0 |
```

Живой подписанный bootstrap содержит не один, а четыре entry: стабильный домен, прямой IP и два HTTPS edge. Панель показывала ровно один из-за blind spot в измерении: Core сам проверял только `https-direct`, Android проверял домены VPN-нод, но не перебирал entry Control Plane, а серверная allowlist отбрасывала device report по IP и edge.

«Отсюда 100%» значит, что мы достаём сами себя. Про доступность из России это не говорит ничего — ради этого различия и заведены две точки обзора, и оно уже один раз показало блокировку, невидимую изнутри.

**Чем рисковало.** Устройство спрашивает путь входа, когда ему нужно узнать, куда идти дальше: первая установка, смена нод, восстановление после блокировки. Уже подключённые живут на выданном плане и ничего не заметят — а новая установка не заработает вовсе. Отказ выглядит как «приложение не работает у новых пользователей», при полностью здоровом сервисе.

На 2026-08-30 из внешней точки сначала отвечали стабильный домен, прямой IP и один edge. У `n-c5e6` оказался остановлен `nginx`: management SSH и сама нода оставались живы, а её публичный edge получал connection refused. Штатный `Update Node` дополнен восстановлением HTTPS-сервиса и применён с rollback-таймером; после его health/privacy checks все четыре точных bootstrap URL отвечают HTTP 200 с валидным TLS. Новая нода не нужна: уже есть четыре рабочих маршрута, в том числе edge на отдельных нодах; добавление пятого адреса не исправляло бы отсутствие измерения.

**Исправление:** Android ограниченно по частоте проверяет каждый entry из последнего подписанного descriptor напрямую из пользовательской сети и отправляет только `host` нашего entry, результат и latency. Core принимает только цели из собственной таблицы включённых bootstrap entries/нод. Попытки через VPN в эту метрику не входят.

**Живая приёмка:** после развёртывания Core test APK установлен и открыт на целевом устройстве из России с выключенным VPN. [Read The Panel run 33328529066](https://github.com/ai-zaytsev/simple/actions/runs/33328529066) показал четыре включённых bootstrap entry: отдельные пути №1 и №5 получили соответственно `6` и `4` device checks с успехом 100%; entries №3 и №4 одновременно являются прикрытиями нод и получили `7` и `11` checks с успехом 100% и 91%. Обе ноды вернулись в `works`, обе выдаются, заблокированных и неисправных нод — ноль.

Критерий выполнен: путей входа больше одного, каждый проверен с устройства из целевой сети, пользовательский трафик для этого не логируется.
