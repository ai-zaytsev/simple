# Control Plane

Серверная часть, которая решает, куда подключается приложение. Реализация того, что спроектировано на Стадии 1: [remote-config.md](../docs/architecture/remote-config.md), [bootstrap-recovery.md](../docs/architecture/bootstrap-recovery.md).

## Что Он Отвечает

| Запрос | Что возвращает |
| --- | --- |
| `POST /v1/plan` | план подключения для одного устройства: основная нода и резервы |
| `GET /v1/config` | поведение приложения: kill switch, минимальная версия, флаги |
| `GET /v1/bootstrap` | где искать этот сервис в следующий раз |
| `GET /healthz` | жив ли процесс |

Все три документа подписаны. Приложение принимает их **только** из-за подписи ключом, вшитым в сборку, и ни по какой другой причине.

## Настройка Через Окружение

Ни у одного параметра нет значения по умолчанию, при котором сервис стартует наполовину настроенным. Отсутствие любого — отказ при старте, а не отказ потом, когда устройство уже ждёт ответа.

| Переменная | Что это |
| --- | --- |
| `CP_DATABASE_URL` | строка подключения к PostgreSQL |
| `CP_SIGNING_KEY_ID` | идентификатор ключа, попадает в документ как `key_id` |
| `CP_SIGNING_SEED` | приватная половина, base64, 32 байта |
| `CP_BOOTSTRAP_HOSTS` | через запятую: куда клиентам обращаться в следующий раз |
| `CP_LISTEN` | адрес прослушивания, по умолчанию `127.0.0.1:8080` |

Слушает loopback: наружу его выставляет nginx, который держит сертификат. Сервису не нужно знать ни про TLS, ни про домен.

## Три Решения, Которые Легко Потерять При Правках

**Счётчик документов живёт в базе, а не в процессе.** Инвариант И-2. При втором экземпляре сервиса счётчик в памяти начал бы выдавать одинаковые или убывающие номера, и клиенты стали бы отбрасывать валидную конфигурацию как попытку отката. Сделано транзакционно сейчас, когда экземпляр один и это ничего не стоит, потому что задним числом это уже не исправить: у флота клиентов будет записан номер, который никому не перекрыть.

**Каждый выданный документ сохраняется.** Это и есть механизм возврата к предыдущей рабочей конфигурации. Клиент отвергает всё, что движется назад по номеру, поэтому «откатиться» означает **выдать старое содержимое заново под новым, большим номером**. Без сохранённого содержимого выдавать было бы нечего.

**Подписывается ровно та последовательность байтов, которую разбирает клиент.** Полезная нагрузка едет закодированной, а не вложенным JSON: повторная сериализация разобранного документа может переставить поля или изменить пробелы, и подпись перестала бы сходиться на документе, который никто не трогал.

## Чего Здесь Нет

- **выбора клиентом.** DNS, маршрутизация, таймауты, пороги переключения заданы сервером. Клиент, который их выбирает, — это клиент, принимающий решения
- **географии в плане.** Ни страны, ни провайдера, ни региона: план не должен позволять судить о размере и форме флота
- **адреса ноды как имени.** Только числовой адрес, `ADR-028`. Имя пришлось бы разрешать до того, как туннель существует

## Локально Не Собирается

На машине разработчика нет Go. Сборка и проверка — в конвейере, как и у остальных Go-модулей проекта.

## Что Должно Быть На Хосте

Развёртывание ставит бинарник, пишет unit и применяет схему. Всё остальное — настройка хоста, и nginx в неё входит.

Сервису нужны два маршрута наружу:

```nginx
location /v1/ { proxy_pass http://127.0.0.1:8080; proxy_http_version 1.1; proxy_set_header Host $host; }
location = /a { proxy_pass http://127.0.0.1:8080; proxy_http_version 1.1; proxy_set_header Host $host; }
```

`/a` — ссылка из письма. Её легко забыть: без неё сервис отвечает, планы выдаются, здоровье зелёное, и не работает ровно одно — вход. Поэтому развёртывание проверяет её снаружи, по настоящему имени, и падает, если получен 404.

## Схема

Миграции лежат в `internal/store/migrations/` и вкомпилированы в бинарник. Применяются при старте, до того как сервис начинает отвечать, под advisory-локом, каждая в своей транзакции; применённые записываются в `schema_migrations` и второй раз не выполняются.

Отдельного шага «применить миграции» нет намеренно: он был шагом, который можно забыть, а забытый шаг означает работающий бинарник поверх схемы, которой он не соответствует.

## Открытие Ссылки Оставляет След

```nginx
log_format confirm '$time_iso8601 $status $request_method $uri $request_time $ssl_protocol';

location = /a {
    access_log /var/log/nginx/confirm.log confirm;
    ...
}
```

Что записывается: когда, с каким статусом, сколько заняло, какая версия TLS. Чего нет и не должно быть: **строки запроса** — в ней токен, то есть весь ключ от аккаунта, — и адреса клиента. `$uri` это путь без параметров, поэтому токен не попадёт сюда даже случайно.

Зачем: ссылка, которая не сработала, не оставляла следа нигде. По базе видно, что попытка не была израсходована, и это доказывает, что запрос не дошёл до приложения. Но не различает «дошёл до машины и был отвергнут» и «не дошёл вовсе», а у этих двух разные причины.
