# Plan: Heavy Users Load Shape

## Порядок

1. Проверить, что уже работает, прежде чем что-либо строить.
2. Проверить механизмы, на которых будет держаться новое: маршрутизация по пользователю, подмена правил на живом движке.
3. Строить только то, что подтвердилось.

Второй пункт окупился: подмена правил на живом движке падает, и узнать это до проектирования дешевле, чем после.

## Риски

**Когорта превращается в ключ.** Закрыто в базе: колонка принимает два значения и отвергает третье. Тест читает миграцию и падает, если ограничение исчезнет.

**Группа из трёх человек.** Панель отказывается показывать что-либо, пока в каждой группе не наберётся достаточно людей, и называет причину.

**Перезапуск движка бьёт по пользователям.** Агент ждёт момента, когда никто не подключён. Ожидание ограничено шестью часами.

**Плохой список ломает маршрутизацию.** Структуру правил строит сама нода; из Control Plane приходит только перечень учётных данных. Ошибочный перечень может отнести пользователя не в ту группу и не может сломать таблицу.

## Валидация

- Рукопожатие BitTorrent через туннель → `class-p2p`, целиком.
- Два клиента с разными учётными данными → байты в разных счётчиках.
- `adrules` → паника, правила не подменились: механизм отвергнут по результату опыта.
- Тест схемы падает, если ограничение на две группы уберут.
