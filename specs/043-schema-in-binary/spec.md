# Spec: Schema In The Binary

Схема базы перестаёт быть папкой файлов, которые кто-то применяет руками перед развёртыванием.

## Что Было Не Так

Работающий код и схема, которая ему нужна, были двумя вещами, которые держались в соответствии только памятью человека. Забытый шаг не виден: сервис стартует, здоровье зелёное, и ломается по одному запросу за раз — на первом обращении к колонке, которой нет.

## Как Сейчас

Файлы миграций лежат внутри пакета `store` и вкомпилированы в бинарник. Применяются при старте, до того как сервис начинает отвечать.

- **Advisory-лок**, чтобы два одновременно стартующих экземпляра не мигрировали оба.
- **Транзакция на файл**: упавшая на середине миграция оставляет схему такой, какой она была, а не в состоянии, которого не описывает ни один файл.
- **Таблица `schema_migrations`**: файл выполняется один раз. Это то, что позволит будущей миграции сделать неповторяемое — заполнить колонку, снять default — не требуя от автора писать её так, чтобы она пережила второй запуск.

Первая миграция уже применена на работающей базе без записи в журнале. Она выполнится ещё раз — она для этого написана — и после этого будет записана.

## Маршрут Ссылки

`/a` — адрес из письма. Nginx о нём надо сказать отдельно, и его легко забыть: без него сервис отвечает, планы выдаются, здоровье зелёное, и не работает ровно вход. Развёртывание теперь проверяет его снаружи, по настоящему имени, и падает на 404.

## Ещё Одна Правка

Лимит на отправку отвечает точно так же, как успех — иначе он сам стал бы способом отличить настоящий адрес. Но идентификатор попытки при этом выдавался случайный, ни к чему не привязанный: приложение опрашивало его, получало «нет такой» и показывало «ссылка устарела» — при том что в почте лежало до пяти рабочих ссылок. Теперь возвращается идентификатор живой попытки этого же устройства, и экран говорит правду.
