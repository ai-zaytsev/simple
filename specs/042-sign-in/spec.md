# Spec: Sign In

Стадия 4. Регистрация и вход за минимум действий: адрес почты, письмо, ссылка, готово.

## Ресурс От Business Owner

**Не требуется.** Почтовый сервис уже есть: Brevo подключён на Стадии 1, домен `mail.simple-vpn.download` аутентифицирован, отправка проверена, отслеживание открытий и переходов выключено. См. [../../docs/integrations/brevo.md](../../docs/integrations/brevo.md).

## Чего Нет

Пароля, повторного пароля, кода из письма, PIN, логина. Ничего из этого не появится и позже: то, что защищает пароль, — это доступ к почтовому ящику, в чём признаётся любая процедура восстановления. Ящик используется напрямую, а не как запасной путь.

## Три Правила Сервера

**Ответ одинаков всегда.** Есть у адреса аккаунт, нет его, исчерпан лимит, не удалось отправить — ответ один и тот же. Иначе приложение становится способом спросить «этот человек ваш клиент?», а отказ, который возникает только на настоящих адресах, — это и есть такой способ.

**Аккаунт создаётся при переходе по ссылке, а не при запросе.** Иначе любой мог бы создать аккаунт на чужой адрес, и само существование аккаунта стало бы тем, что противник может вызвать, а не только узнать.

**Ссылка хранится хешем и тратится в транзакции с блокировкой.** Чтение базы не даёт ничего пригодного, а два перехода по одной ссылке не могут оба застать её неиспользованной.

## Что Требовало Отдельного Решения

| Требование | Как выполнено |
| --- | --- |
| Письмо не пришло | Кнопка повторной отправки, доступна через минуту |
| Ошибся в адресе | Кнопка «Изменить адрес» без перезапуска |
| Ссылка открыта на компьютере | Приложение **спрашивает** сервер, а не ждёт события: телефон и компьютер не знают друг о друге |
| Повторный ввод адреса | Аккаунт ищется по нормализованному адресу, новый не создаётся |
| Переустановка | Новый `device_id`, тот же аккаунт по адресу |
| Каждая установка подтверждается | `device_id` новый при установке, привязки нет, вход обязателен |
| Ссылка одноразовая и срочная | 15 минут, `consumed_at` в транзакции |

## Закрытая Дыра

План выдавался по идентификатору аккаунта, который присылал клиент. Это была не аутентификация, а заявление, которое мог сделать кто угодно. Теперь аккаунт берётся из привязки устройства: без подтверждённого адреса план не выдаётся вообще.

## Принято

Проверено на устройстве Business Owner, подтверждено данными на сервере: три подтверждения с двух устройств, **аккаунт один**.

| Что требовалось | Чем подтверждено |
| --- | --- |
| Новый пользователь: установка → адрес → ссылка → ON | Подтверждение в 19:17:07, туннель в 19:17:23 |
| Повторный ввод адреса не создаёт второй аккаунт | Две попытки с первого устройства, один аккаунт |
| Переустановка восстанавливает аккаунт | Новое устройство `02b9…`, тот же аккаунт `9ca2…` |
| Каждая установка подтверждается отдельно | Новая установка потребовала новой ссылки |
| Ссылка одноразовая | Все три попытки помечены израсходованными |

Сессия после входа чистая: 61 запрос через туннель, 44 ответа DNS на 42 запроса, 14 блокировок по правилам. Единственные отказы — поиск IPv6-адреса для `get-v6.2ip.io`: IPv6 не маршрутизируется, и пустой ответ здесь правильный. На сайтах проверки IP строка IPv6 останется пустой — это не утечка, а её отсутствие.

## Убрано

Семь аккаунтов, оставшихся от Стадии 3, когда клиент сам называл свой аккаунт. Привязанные к ним устройства получали план, ни разу не подтвердив адрес, — это противоречило правилу, что каждая установка подтверждается отдельно. Удалены вместе с привязками; проверено, что подтверждённое устройство план получает, а удалённое получает 401.
