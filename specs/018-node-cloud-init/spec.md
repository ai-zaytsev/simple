# Spec: Node Cloud Init And Full Verification

- Feature ID: `018-node-cloud-init`
- Feature Branch: `feature/018-node-cloud-init`
- Status: `in-progress`

## Goal

Собрать ноду так, как она будет собираться в проде: Nginx с настоящим сайтом, VLESS через WebSocket на выделенном пути, REALITY на отдельном порту как запасной транспорт. Проверить оба транспорта фактическим прохождением трафика.

## Схема Ноды

```
:80   Nginx  -> редирект на 443, плюс ACME webroot
:443  Nginx  -> /            сайт о городских голубях
             -> /<ws-path>   WebSocket -> Xray на 127.0.0.1
:8443 Xray   -> VLESS + REALITY, запасной транспорт
```

## Сертификаты

Проверочная нода выпускает сертификат сама, через HTTP-01, ключ рождается на ноде и не покидает её. Это работает, потому что домен здесь принадлежит одной ноде.

В проде домен делит группа нод, и HTTP-01 валидировал бы ту ноду, на которую сейчас указывает A-запись. Поэтому в проде схема другая: DNS-01, оркестрованный Core, учётные данные DNS на ноды не выдаются. `ADR-023`.

Выпуск идёт в staging-контуре Let's Encrypt. Ограничение в пять сертификатов на идентичный набор имён за семь дней означает, что цикл «создать, проверить, удалить» на боевом контуре израсходовал бы недельный лимит домена за один день. Это закреплено предусловием в Terraform: создать проверочную ноду с боевым контуром нельзя.

Клиент проверки не отключает проверку сертификата, а добавляет staging-корень в доверенные. Проверка, которая пропускает валидацию, не проверяет то, ради чего делается.

## Что Проверяется

1. Сайт отвечает по TLS, и отданная страница побайтово совпадает с той, что лежит в репозитории.
2. **Путь туннеля неотличим от несуществующей страницы**: совпадают код ответа, тело и набор заголовков.
3. Трафик проходит через WebSocket и выходит с адреса ноды.
4. Трафик проходит через запасной REALITY и выходит с адреса ноды.

Вторая проверка — главная из новых. Противник по threat model имеет аккаунт и знает путь; путь не секрет. Чем он не должен быть — это сигналом: отличие в коде, заголовках или времени ответа превращает его в детектор для любого, кто путь угадает.

## Два Логирования, Выключенных В Генераторе

- access log Xray: содержит каждый адрес назначения
- access log Nginx: содержит адреса клиентов

Оба выключены там, где рождается конфигурация, поэтому включить их в рантайме нечем. Клиентский адрес также намеренно не передаётся в Xray заголовками: он там не нужен, а передача положила бы адреса туда, где их можно записать.

## Non-Goals

- не разворачивать Core: DNS-01 через него — следующий шаг
- не выпускать боевые сертификаты
- не оставлять ноду работающей

## Acceptance Criteria

- нода поднимается без ручных шагов
- сайт отдаётся по TLS и совпадает с репозиторием
- путь туннеля неотличим от несуществующего
- оба транспорта пропускают трафик
- нода и DNS-запись удаляются, в аккаунте не остаётся дроплетов
