# Plan: Control Plane

## Ресурсы, Которые Нужно Подтвердить

### 1. Хост для Control Plane

**Что требуется.** Одна машина, на которой живут Core и PostgreSQL.

**Зачем.** Приложение обращается к ней за планом подключения. Без неё Стадия 3 не существует.

**Минимальные требования.** 1 vCPU, 1 ГБ памяти, 20 ГБ диска. Для ~50 пользователей и небольшой базы этого достаточно с запасом.

**Ключевое ограничение.** Адрес должен быть в чистом диапазоне: телефон обращается к Core **до того, как туннель поднят**, напрямую. Крупное облако не подходит по той же причине, по которой не подошло для входных нод — см. [network-path.md](../../docs/architecture/network-path.md).

**Предложение — сервер `fi`.** Он уже оплачен, уже принадлежит вам, его путь из России измерен и здоров, и Стадия 1 уже планировала разместить Core и PostgreSQL именно на нём. Новых расходов не требуется.

**Какой доступ нужен.** SSH — уже есть.

**Секретный ли доступ.** Нет.

### 2. Домен для Control Plane

**Что требуется.** Имя, по которому приложение обращается к Core, и желательно второе — на другом регистраторе.

**Зачем.** Канал `https-direct` из [bootstrap-recovery.md](../../docs/architecture/bootstrap-recovery.md). Второе имя нужно потому, что четыре точки входа у одного регистратора — это одна точка входа.

**Предложение.** Взять два из имеющихся `.xyz`: они у разных регистраторов, покупать ничего не нужно. Это делает их не расходными входными доменами, а инфраструктурными — стоит зафиксировать явно.

**Открытый вопрос.** `simple-vpn.download` не управляется ни одним из подключённых провайдеров DNS: его зона обслуживается где-то ещё. Для канала восстановления это пробел. Нужно знать, где он, до того как понадобится срочно.

**Секретный ли доступ.** Нет, имена доменов публичны по построению.

### 3. Бюджет Kamatera

**Что требуется.** Решение по месячной сумме на входные ноды.

**Зачем.** Диапазоны DigitalOcean не пропускают трафик из России, проверено на шести регионах. Входные ноды должны жить у провайдера с чистым диапазоном.

**Сколько.** Сейчас пополнено $10, работает одна машина. Одна нода непрерывно — единицы долларов в месяц.

**Секретный ли доступ.** Ключи API уже в секретах репозитория.

### 4. Ключи подписи

**Что требуется.** Пара ключей Ed25519 для подписи документов, плюс вторая пара для ротации.

**Зачем.** Приложение принимает настройки только с валидной подписью.

**Кто создаёт.** Мы, командой. Покупать нечего.

**Какой доступ нужен.** Приватный ключ — секрет репозитория, публичные вшиваются в APK.

**Секретный ли доступ.** Приватный ключ — да, и это самый чувствительный секрет проекта: он позволяет выдать любому клиенту любую точку входа.

## Порядок Работ

Не начинается до подтверждения ресурсов.

1. Схема базы: устройства, аккаунты, ноды, планы, `seq` как транзакционный счётчик.
2. Core: выдача плана, remote config, bootstrap descriptor, подпись.
3. Клиент: получение и проверка плана, хранение `seq`, состояния плана.
4. Удаление чтения точки входа из ассета сборки.
5. Проверка приёмки: замена ноды на стороне сервера, приложение переезжает без обновления.

## Риски

- **Один экземпляр Core — единая точка отказа.** Состояние `GRACE` из [remote-config.md](../../docs/architecture/remote-config.md) не даёт этому отключить уже работающих пользователей, но новые подключения при недоступности Core невозможны.
- **Один хост для Core и базы.** Компрометация одного даёт оба. Для MVP принято, для роста — разносить.
- **Одно имя `https-direct` вместо двух.** Пока не подтверждено второе, канал входа один.
