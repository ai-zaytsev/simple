# Plan: Переключение на боевой магазин

## Порядок

1. Выкат Core → `YOOKASSA_PROD_*`.
2. Сверка → тот же магазин.
3. Проверка `test`-флага → сравнение сторон вместо запомненного `true`.
4. Тесты на боевой платёж и на расхождение сторон.
5. Guard про один магазин, испытанный подделкой.
6. Стендовые workflow оставлены на тестовом, причина написана рядом.

## Риски

**Первый настоящий платёж отклонён из-за чека.** `Create` не шлёт объект `receipt`. Боевой магазин с фискализацией на стороне ЮKassa может его требовать; освобождённый — нет. Определить это из репозитория нельзя, зависит от настроек магазина. Названо явно и передано Business Owner.

**Веб-хук не заведён на боевом магазине.** Тогда Core узнает о платеже не сразу, а при следующем `GET /v1/payments/current`: `Current` перечитывает у провайдера всякий незакрытый платёж. То есть VIP не потеряется, но включится позже. Проверить настройку всё равно надо.

**Проверка `test`-флага ослаблена.** Была «оба true», стала «обе стороны согласны». Строгость не потеряна: расхождение — это ровно случай, когда Core и провайдер говорят о разных магазинах, то есть отказ, который может вызвать само переключение. Закреплено двумя тестами.

**Стендовые инструменты выглядят забытыми.** Причина написана в самом файле, рядом с ключами, а не в спеке.

## Валидация

Guard испытан подделкой: сверке подставлен тестовый магазин при боевом выкате — найдено и названо.

Python локально недоступен, тесты скриптов гоняет baseline. Настоящая проверка — первая покупка на боевом магазине, и она за Business Owner.
