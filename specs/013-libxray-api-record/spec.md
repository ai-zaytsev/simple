# Spec: libXray API Record

- Feature ID: `013-libxray-api-record`
- Feature Branch: `feature/013-libxray-api-record`
- Status: `implemented`

## Goal

Зафиксировать результат первой сборки транспортного движка: закреплённые версии, контрольную сумму и фактическую публичную сигнатуру.

## Установленные Факты

- libXray собран из исходников XTLS, коммит `68119ddec6a16ea635838af0e9e11fd93316812c`
- Xray-core закреплён через `go.mod`: `v1.260327.1-0.20260728075948-5ca6f4b7d4dc`
- AAR: 95 485 903 байта, SHA-256 `cc2d82586569adce1e5bf83df2674d0c1215641b612eb62142dd98568a3063d3`
- управление движком идёт через единственный `invoke(String): String`, а не через набор типизированных методов
- движок предоставляет `DialerController.protectFd(long)`

## Два Следствия

**Контракт с движком — формат команды, а не сигнатура метода.** Ошибка в имени команды не ловится компилятором, поэтому набор используемых команд должен закрываться тестом.

**Появился второй механизм защиты от петли.** `protectFd` отдаёт каждый сокет на защиту через `VpnService.protect()`. Он независим от исключения приложения из туннеля и будет использован вместе с ним: петля не деградирует соединение, а делает его неработоспособным незаметно.

## Что Осталось

Словарь команд `invoke` не виден в Java-сигнатуре и задан в Go-исходниках. Пока он не выяснен, привязка не пишется: код по догадке соберётся и не заработает, а отличить это от сетевой проблемы на устройстве дороже, чем прочитать исходник.

## Acceptance Criteria

- версии, контрольная сумма и сигнатура зафиксированы в durable memory
- следствия для привязки записаны явно
