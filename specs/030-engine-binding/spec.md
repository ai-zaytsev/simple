# Spec: Engine Binding

- Feature ID: `030-engine-binding`
- Feature Branch: `feature/030-engine-binding`
- Status: `in-progress`

## Что Сделано

Написана привязка к движку по фактическому контракту, извлечённому из исходников закреплённой версии:

```
{"apiVersion": 2, "method": "runXray", "payload": {"xrayJson": "..."}}
{"apiVersion": 2, "method": "stopXray"}
{"apiVersion": 2, "method": "getXrayState"}
```

Ответ всегда проверяется. Контракт здесь — формат сообщения, а не сигнатура метода, поэтому опечатка в имени команды компилируется и падает только в работе; имена собраны в закрытый перечень.

Подключён `protectFd`: движок отдаёт каждый свой сокет системе на защиту. Это второй, независимый рубеж против петли маршрутизации, рядом с исключением приложения из туннеля.

Сборка AAR встроена в сборку приложения и кэшируется по закреплённому коммиту: собирается один раз на версию движка, а не на каждый прогон.

## Найденное Ограничение

В libXray нет работы с TUN. Проверено по дереву исходников закреплённой ревизии: 78 файлов, ни одного упоминания.

Движок поднимает Xray и локальный прокси внутри процесса приложения. Забирать пакеты с сетевого интерфейса телефона и передавать их в этот прокси должен отдельный компонент, которого в проекте нет.

Следствие: с одной этой привязкой приложение установит соединение с нодой, но трафик устройства через него не пойдёт. Требование Стадии 2 без недостающего компонента не закрывается.

## Non-Goals

- не добавлять мост TUN в этой задаче: это отдельный компонент со своей сборкой

## Acceptance Criteria

- приложение собирается с движком внутри
- отчёт сборки показывает, что движок вложен в APK

## Validation

- сборка APK в CI
