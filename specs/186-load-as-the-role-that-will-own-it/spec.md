# Spec: Загружать той ролью, которой это будет принадлежать

- Feature ID: `186-load-as-the-role-that-will-own-it`
- Feature Branch: `feature/186-load-as-the-role-that-will-own-it`
- Status: `local-ready`

## Что Отказало

```
ERROR: cannot reassign ownership of objects owned by role postgres
       because they are required by the database system
```

Хорошая новость в форме отказа: **зависания больше нет**. Предыдущая правка сработала — запуск упал за секунды с внятной ошибкой вместо шестнадцати минут молчания.

## Почему `REASSIGN OWNED` Не Мог Сработать

Я загружал дамп суперпользователем и собирался передать владение после. Но `postgres` владеет не только тем, что создал этот дамп, — ему принадлежат объекты, нужные самой СУБД. Команда отказывается целиком, а не переназначает подмножество.

Замысел был неверен по существу, а не в деталях: **владение нельзя починить после, если чинить его приходится у суперпользователя.**

## Решение Проще Того, Что Было

Задать роль **до** загрузки.

```
{ printf 'set role %s;\n' "${owner}"; cat dump; } | psql
```

Объекты принадлежат тому, кто их создаёт. `psql` работает суперпользователем — подключаться ролью сервиса значило бы обращаться с её паролем, чего этот workflow намеренно не делает, — а `set role` переключает права на всю сессию. Суперпользователь создаёт всё уже от имени `core`, ни разу не аутентифицировавшись как `core`.

Одна строка вместо отдельного шага, и она не может отказать по причине, по которой отказал `REASSIGN`.

## Что Осталось Прежним

Проверка после загрузки: роль сервиса обязана прочитать `schema_migrations` **до обмена**. Не смогла — временная база удаляется, боевая не тронута.

Именно она и должна теперь подтвердить, что владение верное, — на том же самом вопросе, на котором сервис падал.

## Готовность

- дамп загружается ролью, которой база будет принадлежать
- проверка прав проходит до обмена
- восстановление в бой выполнено целиком
