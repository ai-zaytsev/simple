# Spec: Проверка ЮKassa и возвраты VIP

- Feature ID: `157-yookassa-refunds`
- Feature Branch: `feature/157-yookassa-refunds`
- Status: `merge-ready`

## Цель

Полностью проверить существующий тестовый платежный контур и добавить возвраты VIP. Core определяет право на возврат и точную сумму, а платежный провайдер только выполняет денежную операцию. Возврат всегда идет через провайдера исходного платежа.

VIP прекращается только после канонически подтвержденного успешного возврата. Ошибка, незавершенный запрос, потеря ответа или неподтвержденное событие VIP не меняют.

## Политика Возврата

1. От момента подтвержденной оплаты до границы ровно `7 × 24 часа` включительно возвращается 100% исходной суммы.
2. После этой границы и до конца оплаченного периода возвращается `оплаченная сумма × оставшийся срок / полный оплаченный срок × 75%`.
3. Расчет выполняется в целых копейках; дробная копейка отбрасывается вниз, поэтому возврат никогда не превышает результат политики.
4. После окончания оплаченного периода автоматического возврата нет.
5. Если рассчитанная сумма ниже минимальной суммы возврата исходного провайдера, Core не округляет ее вверх и не отключает VIP, а возвращает явный отказ с причиной.
6. После подтвержденного успешного возврата оставшийся VIP прекращается.

## Функциональный Контракт

- Android передает только идентификатор исходного платежа и явное согласие на retry после канонической отмены; стабильный логический refund ID и provider idempotency keys создаёт Core. Сумму и провайдера определяет Core.
- Core хранит снимок оплаченного периода, расчет, логический запрос возврата и историю попыток у провайдера.
- Один пользовательский запрос нельзя исполнить дважды; сумма успешных возвратов не может превысить исходный платеж.
- Потерянный ответ провайдера повторяется с тем же idempotency key и не создает вторую денежную операцию.
- Перед повторным POST Core ищет refund в provider list по исходному payment ID и своему metadata ID; после окончания 24-часового окна идемпотентности ЮKassa новый POST вслепую запрещён.
- Явно отмененную попытку можно повторить отдельной попыткой с новым idempotency key, сохранив историю предыдущей.
- Ответ API или webhook является только поводом для сверки; финальное состояние читается через серверный API провайдера.
- Возврат применим только к успешному платежу правильного аккаунта, который действительно выдал VIP.
- Секреты провайдера доступны только Core/CI и не попадают в Android, код, документацию, PR или логи.

## Универсальность

Доменная модель возврата, расчет политики, публичный Core API и Android не содержат логики ЮKassa. Provider contract поддерживает создание и чтение возврата, а реестр провайдеров выбирает adapter по `provider` исходного платежа. Это позволяет завершать возвраты старого провайдера после переключения новых продаж на другой.

ЮKassa adapter использует штатный refunds API, исходный способ оплаты и provider-specific ограничения. Эти ограничения переводятся в нейтральные состояния и причины Core.

## Проверка Платежей

На тестовом магазине проверяются успешная, неуспешная и отмененная оплаты; webhook и его повтор; однократная активация VIP; связь платежа с нужным аккаунтом; отсутствие изменения VIP при ошибках.

## Проверка Возвратов

Проверяются полный и частичный возвраты, канонический статус, ошибка и повтор, недостаточный баланс магазина, корректность суммы, исходный способ оплаты, потеря ответа и повторная доставка событий. Для реально использованных способов оплаты отдельно фиксируется поддержка частичного возврата.

Границы расчета: сразу после оплаты, ровно через 7 дней, после 7 дней, почти в конце и после окончания периода.

## Не Входит

- chargeback automation и спорные операции;
- возврат через провайдера, отличного от провайдера исходного платежа;
- изменение цен, сроков продуктов, логики покупки и 7-дневного FREE-периода;
- подписки, автоплатежи, продления и удержание пользователя;
- production-магазин и реальные денежные операции.

## Критерии Приемки

- Core точно и детерминированно применяет политику `0–7 дней: 100%; после 7 дней: pro rata × 75%; после окончания: нет автоматического возврата`;
- полный и частичный возвраты проходят в тестовой ЮKassa через исходный платежный способ;
- повторы и потерянные ответы не создают двойной возврат;
- сумма успешных возвратов не превышает платеж;
- VIP прекращается только после подтвержденного `succeeded` и остается при `pending`, `canceled` и ошибках;
- Android не знает секретов или provider-specific API;
- существующая оплата проходит полный live test matrix;
- PR head проходит required checks, review и не имеет merge conflicts;
- после deploy живые состояния платежей, возвратов и VIP сверены с ожиданием.
