# Spec: DNS Inventory Diagnostics

- Feature ID: `004-dns-inventory-diagnostics`
- Feature Branch: `feature/004-dns-inventory-diagnostics`
- Status: `in-progress`

## Goal

Сделать так, чтобы отказ одного DNS-провайдера не скрывал состояние второго, и чтобы сообщение об ошибке указывало на причину, а не только на код ответа.

## Проблема

Первый запуск `DNS Inventory` упал на шаге проверки Cloudflare с `HTTP 401 Invalid API Token` и завершил job целиком. В результате не выяснилось ничего: ни работают ли учётные данные Spaceship, ни какой провайдер обслуживает какие домены, ни есть ли проксирование.

Ошибка проектирования в том, что проверка учётных данных была gate-шагом, а не источником данных.

## Решение

- проверки обоих провайдеров выполняются независимо и не прерывают job
- инвентаризация выполняется по тем провайдерам, чьи учётные данные работают
- итоговый вердикт подводится последним шагом
- для Cloudflare выполняются две независимые пробы: `user/tokens/verify` и `zones`, потому что они различают недействительный токен и токен с недостаточной областью
- перед отправкой из значений секретов удаляются пробельные символы: вставленный с переводом строки токен даёт неотличимый `401`
- в вывод добавлены наиболее вероятные причины `401` для Cloudflare, включая подстановку Global API Key вместо API Token

## Non-Goals

- не менять DNS-записи
- не подбирать и не восстанавливать учётные данные

## Acceptance Criteria

- запуск с нерабочим Cloudflare-токеном всё равно показывает состояние Spaceship и распределение доменов
- сообщение об ошибке Cloudflare содержит код ошибки провайдера и список вероятных причин
- вердикт падает, если хотя бы один провайдер недоступен

## Validation

- YAML-валидация и проверка ASCII
- фактический запуск после merge
