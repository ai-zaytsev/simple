# Spec: Lightweight ACME And Early Status

- Feature ID: `020-node-lightweight-acme`
- Feature Branch: `feature/020-node-lightweight-acme`
- Status: `in-progress`

## Две Ошибки Предыдущей Попытки

**Первая: swap не помог, потому что причина шире.** Дроплет с 512 MB не тянет установку Nginx вместе с Certbot, который приносит питоновский стек. Swap снижает риск, но правильнее убрать причину.

**Вторая, моя: сервер статуса был помещён в `runcmd`.** `runcmd` выполняется последним, уже после установки пакетов, то есть после того самого apt, который кладёт машину. Замысел «видеть прогресс с первой секунды» не работал по построению: до первого доступного момента нода успевала умереть.

## Решение

**Certbot убран, ACME-клиент — один статический бинарь.** `lego` версии `v5.4.0`, закреплён и проверяется по контрольной сумме из релиза, ровно как Xray. Из пакетов остаётся Nginx и мелочь. Питоновский стек не устанавливается вовсе.

**Сервер статуса перенесён в `bootcmd`.** Этот этап выполняется в init-стадии, до установки пакетов, поэтому прогресс виден с самого начала — включая момент, когда памяти не хватает.

**Swap оставлен.** Он больше не единственная мера, но снимает пик и стоит одну строку.

## Что Меняется В Схеме Сертификатов

Ничего по существу. Ключ по-прежнему рождается на ноде и не покидает её, проверка по-прежнему HTTP-01 для одиночной проверочной ноды, боевой контур по-прежнему DNS-01 через Core. Меняется только исполняемый файл, который это делает.

Адрес для ACME-аккаунта берётся на нашем же домене, если не задан явно: требование клиента удовлетворяется, а личный адрес в репозиторий не попадает.

## Acceptance Criteria

- статус доступен до и во время установки пакетов
- bring-up доходит до `ready`
- сайт, неотличимость пути и оба транспорта проверены

## Validation

- локальный рендер шаблона с учётом экранирования `$${`
